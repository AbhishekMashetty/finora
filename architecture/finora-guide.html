Finora, explained end to end

Finora is a personal-finance SaaS built as five Go microservices, four MongoDB databases, and a Next.js frontend. This page is a single guided tour of the whole thing: what each piece does, how a feature flows from a browser click all the way to the database and back, and why every significant decision was made the way it was. If you have never seen this codebase, start at the top and follow the links.

The dual purpose (this matters for every decision)

Finora has two goals, and the second is the real one:

  1. Product goal — a realistic personal-finance app: registration, JWT auth, accounts, transactions, budgets, savings goals, notifications, reports.
  2. Platform goal (the actual point) — a long-lived, production-shaped distributed system for practicing Kubernetes, Docker, CI/CD, Argo CD, networking, observability, secrets, scaling, and security against something more realistic than a "hello world."

Every architectural choice is judged against the second goal first: does this make the system easier to deploy, observe, scale, and operate later? The finance domain simply gives that infrastructure something non-trivial to run. That is why you will see "heavier" choices (four separate databases, five separate Go modules) preferred over the locally-cheaper option — they mirror what the Kubernetes deployment will look like.

The project's constitution The root CLAUDE.md is the permanent source of truth for how Finora is built (Clean Architecture, one DB per service, REST-only for now, the gateway as sole JWT validator, and more). When code and CLAUDE.md disagree, the code is considered wrong. This guide is a friendlier narration of the same rules, with the runtime flows drawn out.

frontend

:3000 · Next.js

The product UI. Talks only to the gateway; never to a service directly.

The four hard rules that shape all of this

  1. One MongoDB per service, never shared. No service's code or config may point at another service's database. Isolation is physical (a separate container/URI each), not a permission convention. → Data Model
  2. REST only, for now. Services talk synchronously over HTTP/JSON through documented contracts. Async messaging (NATS) is a planned Phase-7 seam — deliberately not built yet.
  3. The gateway is the only JWT validator. Downstream services trust the X-User-Id header the gateway injects. → The Auth Model
  4. Every service is independently deployable. Each has its own go.mod, Dockerfile, health endpoints, and boots without any other service running (its own Mongo excepted).

3 · The lifecycle of one protected request

This is the single most important flow to internalize — almost every feature is a variation of it. Say the browser asks for GET /api/v1/accounts (list my accounts):

  1. Browser → gateway. The frontend's apiFetch attaches Authorization: Bearer <access_token> and calls the gateway at :8080. It never calls :8082 directly.
  2. Gateway validates the token. authmw.RequireAccessToken pulls the bearer token, calls jwtx.Parse(secret, token, "access") — which checks the HS256 signature, the expiry, and that the token type is access. On failure: 401 UNAUTHORIZED, request stops here.
  3. Gateway injects identity. On success it sets X-User-Id from the token's sub claim (always overwriting any client-supplied value) and propagates X-Request-Id. No Authorization header is forwarded downstream.
  4. Gateway routes by path prefix. proxy.Table.Resolve matches /api/v1/accounts to the expense-service proxy (longest-prefix wins), then reverse-proxies the request byte-for-byte.
  5. Service trusts the header. expense-service's router runs middleware.RequireIdentity, which rejects any request missing X-User-Id (401) and otherwise stashes it as the caller's user_id.
  6. Handler → service → repository. The handler reads user_id, calls the service layer, which calls the repository, which runs a Mongo query scoped to that user_id. You can only ever see your own data.
  7. Response envelope flows back. The result is wrapped in the standard {success, data, error, request_id} envelope by httpx.Success, returned through the gateway to the browser, which unwraps data.

The same request, hop by hop — ports & endpoints

Here is that exact GET /api/v1/accounts as concrete network hops. Notice that the path is identical at the browser and at expense-service — the gateway forwards it byte-for-byte and never rewrites it; only the headers change (the Authorization token is dropped, X-User-Id is added).

A multi-service request — the report fan-out, hop by hop

Most requests touch exactly one service. The one that fans out is GET /api/v1/reports/summary: budget-service can't answer it alone, so it calls expense-service (for actual spend) and, if a budget is overspent, notification-service. The narrated version of hops 3–6, with the diagram and the overspend dedup rule, is in the Reports feature ★; the full "who may call whom" matrix is in §14.

Public routes are the exception. register, login, refresh, and password-reset skip steps 2–3 (there's no token yet) — the gateway proxies them straight through to user-service, which authenticates them by other means (credentials or the refresh token itself).

Why this shape Centralizing JWT validation at the gateway means the four backend services never touch tokens, secrets rotation, or JWKS — they just trust one header on the internal network. It's simpler and faster than every service re-validating a token. The cost is that the trust boundary is the network: backend ports must be unreachable from outside. That trade-off is documented, and per-service validation is a Phase-9 hardening candidate. See Security Posture for the current gap here.

4 · Clean Architecture, strictly

Every Go service (except the gateway) is built the same way, and understanding this one pattern lets you read all four. The core idea: dependencies point inward. Inner layers know nothing about outer layers.

handler HTTP in/out
→
service business logic
→
domain interfaces + entities
←
repository MongoDB

Everyone depends on domain. domain depends on nothing — no Gin, no Mongo driver, no framework.

LayerIts one jobAllowed to import
domainDefine the entities (e.g. User, Transaction) and the interfaces for repositories and services. Zero framework imports.Only the Go stdlib.
repositoryImplement the domain repository interfaces against MongoDB. The only layer that knows Mongo exists.domain, mongo-driver.
serviceThe use-cases / business logic. Depends only on domain interfaces, never a concrete Mongo type — so it's unit-testable against fakes.domain.
handlerParse & validate the HTTP request, call the service, translate the result into the envelope. Does no business logic. The only layer (with router) that knows HTTP exists.domain, service, Gin, httpx.
routerRegister routes, wire the middleware chain, mount health endpoints.handlers, middleware, Gin.
configLoad & validate env vars (wrapping shared/config).shared/config.

The SOLID payoff: Dependency Inversion

The service layer depends on an interface declared in domain, and the concrete Mongo type implements that interface. That inversion is what makes the whole test strategy work: a service test injects a hand-written in-memory fake instead of Mongo, so go test ./... is fast and needs no database. The report service is the clearest example — it depends on a domain.ExpenseClient interface, so tests inject a fake instead of standing up a real expense-service.

The design principles, in one place

  • No clever code. Optimize for the engineer reading it in two years, not for fewest lines. If a simpler, more explicit version exists, use it.
  • Errors are values, handled at the boundary. Business logic returns typed domain errors (ErrNotFound, ErrDuplicateEmail, validation errors); handlers translate them to envelope error codes. Panics are a safety net (middleware.Recovery), never control flow.
  • Every significant decision is documented with its rationale and the rejected alternative — "we picked X over Y because Z." That's why the architecture/*.md files read the way they do.
  • Don't add complexity before there's a legitimate reason. Redis, NATS, tracing — all deferred to later phases with a documented seam, not built speculatively.

5 · The layer flow, traced through real code

Let's watch one write — POST /api/v1/transactions — fall through the layers of expense-service. This shows exactly where each responsibility lives.

① handler — transaction_handler.go

Binds JSON, reads the caller's user_id from the identity middleware, parses the date, and hands a typed input to the service. It makes no ownership or business decisions itself.

userID := middleware.UserID(c)
var req transactionRequest
if err := c.ShouldBindJSON(&req); err != nil {
    httpx.Fail(c, 400, httpx.CodeValidation, "invalid request body", ...)
    return
}
date, ok := parseDate(req.Date)     // RFC3339 or YYYY-MM-DD
tx, err := h.svc.Create(ctx, userID, domain.CreateTransactionInput{...})

② service — transaction_service.go

All the business rules live here: field validation, and crucially the cross-tenant safety check — the account_id in the body is an unchecked reference until the service confirms that account belongs to this same user.

if err := s.validateCommon(in.AccountID, in.Type, in.Amount, in.Currency, in.Date); err != nil {
    return nil, err                 // typed validation error
}
// the account_id is otherwise an unchecked cross-tenant reference:
if _, err := s.accountRepo.GetByIDForUser(ctx, in.AccountID, userID); err != nil {
    if err == domain.ErrNotFound {
        return nil, NewValidationError("account_id", "account does not exist")
    }
    return nil, err
}

③ repository — mongo_transaction.go

The only Mongo-aware layer. Note every read/update/delete filters by user_id in the query itself — ownership is enforced at the database, not just in app code.

// get / update / delete are ALL scoped like this:
r.col.FindOne(ctx, bson.M{"_id": oid, "user_id": userID})
// a cross-user id simply matches zero documents → domain.ErrNotFound → 404
Why 404 and not 403 for someone else's data When you request a resource you don't own, the query matches nothing and you get 404 NOT_FOUND — never 403 FORBIDDEN. Returning 403 would confirm the resource exists to a non-owner. 404 leaks nothing. This is a fleet-wide rule.

Where it all gets wired: cmd/server/main.go

Each service's main.go is the composition root — it constructs the dependency graph by hand (no DI framework), inner-to-outer: config → mongo connect → repositories → services → handlers → router → health → server.Run. Here's budget-service, the richest example (it also builds two outbound HTTP clients):

budgetRepo   := repository.NewMongoBudgetRepository(db)
goalRepo     := repository.NewMongoGoalRepository(db)
expenseClient := client.NewExpenseHTTPClient(cfg.ExpenseServiceURL)
notifClient   := client.NewNotificationHTTPClient(cfg.NotificationServiceURL)

reportService := service.NewReportService(budgetRepo, expenseClient, notifClient, log)
reportHandler := handler.NewReportHandler(reportService)

r := router.New(log, cfg.CORSAllowedOrigins, budgetHandler, goalHandler, reportHandler, spec, mongoChecker)
server.Run("0.0.0.0:"+cfg.Port, r, log, cfg.ShutdownTimeout)

6 · The shared/ library — the fleet's common spine

shared/ is its own Go module that every service imports. It exists so that cross-cutting behavior (logging shape, response envelope, health probes, identity handling) is written once and can't drift between five otherwise-independent services. Learn these eight packages and you've learned the plumbing of every service.

PackageWhat it gives every service
loggerBuilds a slog JSON logger (logger.New("user-service", level)). Every line carries ts, level, service, request_id, msg. Log-shipper-ready, zero external deps.
httpxThe one response envelope + the six standard error codes. httpx.Success(c, status, data) / httpx.Fail(c, status, code, msg, details). → §7
middlewareRequestID, Logging, Recovery, CORS, and RequireIdentity (+ UserID accessor). The mandated chain and the identity contract.
health/live, /ready, /health handlers + a Checker interface. Liveness never depends on downstream state; readiness pings Mongo. → §16
configEnv-var helpers: MustGetEnv (fail-fast, no default — used for secrets & Mongo URIs), GetEnv, GetEnvDuration, GetEnvInt.
serverAn http.Server wrapper with graceful shutdown on SIGINT/SIGTERM — drains in-flight requests before exit (matters for Kubernetes pod eviction).
jwtxThe single source of truth for the JWT claim shape + GenerateAccessToken/GenerateRefreshToken/Parse. Imported by both the token issuer (user-service) and verifier (gateway) so the contract can't drift.
mongoxThe one way to connect to Mongo (Connect(uri), with a bounded ping) plus a Checker adapter so every /ready behaves identically.

The identity contract, in code

Two tiny functions carry the entire downstream auth model. The gateway sets the header after validating the token; every service requires it:

// shared/middleware/identity.go — every backend route group uses this:
func RequireIdentity() gin.HandlerFunc {
    return func(c *gin.Context) {
        userID := c.GetHeader("X-User-Id")
        if userID == "" { httpx.Fail(c, 401, CodeUnauthorized, "missing user identity", nil); c.Abort(); return }
        c.Set("user_id", userID)     // read later via middleware.UserID(c)
        c.Next()
    }
}

7 · The response envelope & error codes

Every response from every service — success or failure — has the exact same top-level shape, so a client never has to special-case which service it's talking to. This is implemented once in shared/httpx; services are forbidden from hand-rolling a JSON shape.

Success

{
  "success": true,
  "data": { "accounts": [ ... ] },
  "error": null,
  "request_id": "8f3e2c1a-..."
}

Error

{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "email is required",
    "details": { "field": "email" }
  },
  "request_id": "8f3e2c1a-..."

The request_id is the same value echoed in the X-Request-Id response header and in every structured log line for that request — so a user-reported error can be traced across all services by one id.

8 · The auth model (tokens, secrets, trust)

Finora uses a two-token JWT scheme. Understanding the two tokens and where each is validated unlocks the whole auth story.

Access token

type=access · claims {sub, email, type, iat, exp} · TTL 15 min · HS256 with JWT_ACCESS_SECRET. Sent on every protected request as a Bearer token. Validated only by the gateway. Stateless — nothing is stored server-side.

Refresh token

type=refresh · claims {sub, jti, type, iat, exp} · TTL 7 days · HS256 with JWT_REFRESH_SECRET. Exchanged for a new pair when the access token expires. Stateful — its jti is stored (hashed) in Mongo so it can be revoked/rotated.

  • Only user-service issues tokens (on register/login/refresh). Only the gateway verifies access tokens (for routing). Both import shared/jwtx, so the claim shape can't drift between issuer and verifier.
  • Downstream services never see a token. They trust the X-User-Id header the gateway injects, on the internal network. This is the "trust the network boundary" trade-off — simpler than per-service JWKS validation, revisited in Phase 9.
  • The gateway always overwrites X-User-Id with the value from the validated token — a client can never smuggle a fake identity through the gateway.
  • Refresh tokens are stored as a SHA-256 hash of the jti, never the raw token — a database leak alone can't forge a usable refresh token.
Security caveat — read before deploying Because backend services blindly trust X-User-Id, they must be unreachable except through the gateway. In today's docker-compose.yml the service ports (8081–8084) are published to the host, which would let anyone bypass auth with a forged header if exposed to a network. This and other findings are catalogued in §19 · Security Posture and security/security_analysis.md.

9 · gateway :8080 · owns no data

The single public entrypoint. Because it owns no data, its layout differs from the other services — instead of domain/repository/service it has proxy/, authmw/, and router/.

Middleware chain

RequestID → Logging → Recovery → CORS  ( → RateLimit, Phase 6)

Route table

Public routes are declared as explicit static routes and proxied straight to user-service with no auth:

POST /api/v1/auth/register | login | refresh | password-reset  → user-service (public)

Everything else is protected. Rather than a wildcard route (which collides with Gin's radix tree once static auth routes exist), the gateway uses NoRoute — it runs authmw.RequireAccessToken, then a longest-prefix lookup picks the owning backend:

Path prefixOwning service
/api/v1/auth/logout, /api/v1/users/meuser-service
/api/v1/accounts, /transactions, /categoriesexpense-service
/api/v1/budgets, /goals, /reportsbudget-service
/api/v1/notificationsnotification-service

The proxy forwards the request byte-for-byte (path, query, method, body). If a backend is unreachable, the gateway returns a clean 502 envelope ("upstream service unavailable") rather than leaking a raw connection error.

Why CORS lives only here httputil.ReverseProxy copies backend headers with Header().Add. If a backend also set Access-Control-Allow-Origin, the browser would receive it twice as one comma-joined value and reject it. So the gateway is the sole CORS boundary; backend routers run RequestID → Logging → Recovery only. This exact bug shipped once in Phase 0 and was caught only by real browser testing (curl doesn't enforce CORS).

14 · How the services talk to each other (and when)

This is the question that trips up most people reading a microservice repo for the first time, so it gets its own section. The short version: there are only two kinds of traffic in Finora, both plain HTTP/JSON, and almost all of it is the gateway proxying. Actual service-to-service calls are rare, deliberate, and enumerated below — there is no hidden mesh of chatter.

The two kinds of traffic

1 · Gateway → service (proxy)

The dominant traffic. Every client request is validated and reverse-proxied to exactly one owning service by path prefix. The gateway never fans one request out to several services. This is the flow in §3.

2 · Service → service (REST)

Rare and deliberate. Exactly one service (budget-service) calls others, and only for two features. Everything else owns its data and answers only the gateway.

The governing rule A service may only reach another service's data through that service's REST API — never a shared Mongo connection, a borrowed collection, or a backdoor query. That's what keeps each service independently deployable and replaceable. If a feature seems to need an interaction that isn't in the table below, that's a change to service boundaries to be documented — not an ad-hoc shortcut.

The complete "who may call whom" matrix

The two real calls — exactly when each fires

budget-service → expense-service  (when: a report is requested)

  • Trigger: any GET /api/v1/reports/summary. To turn a budget's budgeted amount into actual spend, budget-service has no transaction data of its own — it must ask expense-service.
  • Calls made: GET /api/v1/categories (to resolve the budget's category name → expense-service's category id), then GET /api/v1/transactions?category=<id>&from=&to=&page_size=100, paged up to a 50-page safety cap, summing expense amounts.
  • Code: internal/client/expense_client.go, behind the domain.ExpenseClient interface (so the report service is unit-testable with a fake — Dependency Inversion).

budget-service → notification-service  (when: a report finds a category over budget)

  • Trigger: during that same Summary() computation, the moment a category's remaining < 0. It is not triggered when a transaction is created (there's no event bus yet) — it's a side effect of the read.
  • Call made: POST /api/v1/notifications {title, message, type:"overspend"}, deduplicated per reporting period so a dashboard reload doesn't spam the user.
  • Code: internal/client/notification_client.go, behind the domain.NotificationClient interface. A failure here is logged and swallowed — it never fails the report.

Both are walked step by step, with the diagram and the dedup rule, in the Reports feature ★.

How an internal call authenticates (there's no token)

A service-to-service call does not carry a JWT. Instead budget-service forwards the originating user's X-User-Id header — exactly what the gateway would have injected — and expense-service / notification-service trust it via the same middleware.RequireIdentity they use for gateway traffic. From the callee's point of view an internal call is indistinguishable from a proxied one: same header, same ownership scoping. Each internal call also sets a 3-second timeout, because it's an in-cluster hop that should either answer fast or fail fast.

Why so little service-to-service traffic — and what changes later Finora is deliberately REST-only and low-chatter today: synchronous calls are simple to reason about and debug, and the fewer of them there are, the more independently each service can be deployed and scaled. The overspend notification is the one place this pinches — a GET with a write side effect, which isn't clean REST. That exists only because there's no event bus yet. Phase 7 introduces NATS: the overspend alert becomes a real event published when the triggering transaction is created and consumed by notification-service directly, replacing the read-triggered call. The REST calls for queries (reports reading expense data) stay. See the roadmap.

Feature · Registration

POST /api/v1/auth/register  →  201 {user}. Public route.

  1. Handler validates shape. Gin binding enforces email (valid email), password (min 8 chars), name (required) before any logic runs.
  2. Service normalizes & checks uniqueness. Email is lower-cased and trimmed. It looks up any existing user; a hit returns ErrDuplicateEmail → 409 CONFLICT.
  3. Password is hashed with bcrypt (default cost). The plaintext is never stored or logged.
  4. User + default settings are created. A new User (UUID id) is inserted, then a default Settings doc (USD, UTC) is seeded so GET /users/me/settings never 404s for a fresh account.
  5. Response. The user is returned — with PasswordHash tagged json:"-", so it can never leak into the response even if a handler serializes the struct directly. No tokens are issued on register; the client logs in next.

Feature · Login

POST /api/v1/auth/login  →  200 {access_token, refresh_token, user}. Public route.

  1. Look up by normalized email. If not found, return the same ErrInvalidCredentials as a wrong password would — no user enumeration.
  2. Verify password. bcrypt.CompareHashAndPassword against the stored hash. Mismatch → 401, again with the generic message.
  3. Issue a token pair. issueTokenPair mints an access token (15 min) and a refresh token (7 days) carrying a fresh jti.
  4. Persist the refresh token, hashed. A refresh_tokens record is written storing only SHA-256(jti), the expiry, and revoked: false — this is what makes rotation and revocation possible.
  5. Return both tokens + the user. The frontend stores them and attaches the access token to every subsequent request.

Feature · Anatomy of a protected call

Covered in depth in §3 · Request Lifecycle — this is the reference flow every read/write below inherits. The essence: gateway validates the token and injects X-User-Id → service requires that header → repository scopes the Mongo query to it. You literally cannot query across users; there is no endpoint in the entire system that lists across users.

Feature · Token refresh & rotation (with theft detection)

POST /api/v1/auth/refresh  →  200 {access_token, refresh_token}. This is the most security-critical flow in the app. When an access token expires, the client silently exchanges its refresh token for a brand-new pair.

  1. Parse & type-check. jwtx.Parse(refreshSecret, token, "refresh") validates signature, expiry, and that type == refresh.
  2. Look up the stored record by SHA-256(jti). No record → invalid.
  3. Theft detection ★. If the record is already revoked, someone is replaying a rotated-away token — the legitimate client already moved on to the next token in the chain. The service revokes every refresh token for that user (RevokeAllForUser), forcing full re-authentication on all devices. The client just sees "invalid token."
  4. Expiry check against the stored expires_at.
  5. Rotate. The presented token is revoked before a new pair is issued — so a replayed old refresh token can never succeed twice.
  6. Issue & persist the new pair (new jti, new hashed record) and return it.
Why rotation + reuse-detection matters Rotation means a stolen refresh token is only useful until the real user next refreshes — at which point the thief's copy is revoked. Reuse-detection turns the theft into a tripwire: the moment both the thief and the victim have used the token, all sessions are killed. This was verified live against two real concurrent sessions, not just the in-memory fake.

Feature · Logout

POST /api/v1/auth/logout  →  204. Authenticated by the refresh token in the body (not X-User-Id), and idempotent: a malformed/expired/already-revoked token still returns 204 and never reveals whether the token was ever valid. On a valid, un-revoked token it revokes that one record. Any genuine internal error is the only thing that returns non-204.

Feature · Accounts

Standard owner-scoped CRUD in expense-service. An account is {name, type, currency} where type ∈ {checking, savings, credit, cash}. Listing returns everything unpaginated — deliberately, because a real user has a handful of accounts, not pages of them (adding pagination there would be unjustified complexity). Every read/update/delete is filtered by user_id, so a cross-user id yields 404.

A real bug this domain caught The frontend accounts page once offered investment and other types that expense-service's ValidAccountType rejects — guaranteed 400s. Trimmed to the real four. A good reminder that the backend's validation is the source of truth, not the UI's dropdown.

Feature · Transactions

The highest-volume resource, and the first that paginates. A transaction is {account_id, category_id?, type, amount, currency, date, note}, type ∈ {income, expense}. Traced through the layers in §5. Key behaviors:

  • Cross-tenant safety: on create/update, the service verifies the referenced account_id belongs to the caller before attaching the transaction — otherwise the body could reference someone else's account.
  • Validation: amount > 0, valid type, non-empty currency, a parseable date (RFC3339 or YYYY-MM-DD).
  • Pagination contract: page (default 1), page_size (default 20, capped at 100 server-side). The response echoes the resolved page/page_size the service actually applied plus a total count — not the raw query input.
  • Filtering & sort: by account_id, category (a category id), and a from/to date range; sorted by date descending. Backed by a compound Mongo index (user_id, account_id, date).
The resolved-vs-requested pagination bug Originally the handler echoed the raw ?page= straight back, so omitting it returned page: 0, and page_size wasn't returned at all. Fixed project-wide in Phase 6 by having the service stamp the values it actually applied. This is now the documented standard any future paginated endpoint must follow.

Feature · Categories

Intentionally minimal: create and list only (no update/delete), because that's all the product needs today — a good example of the "don't build what isn't needed yet" principle. A category is {name, type}, owner-scoped. Categories matter most as the join key for reports: budget-service resolves a budget's category name to expense-service's category id to sum spend. See Reports.

Feature · Budgets

Full CRUD in budget-service. A budget is {category, amount, period} (e.g. {"groceries", 500, "monthly"}). The category is a plain name string that matches expense-service's category naming — the two services are joined by name at report time, not by a shared foreign key (they can't share a database). Budgets also carry a hidden, non-API field LastNotifiedAt used by the overspend dedup logic (explained in Reports).

Feature · Savings goals

Full CRUD. A goal is {name, target_amount, target_date, current_amount}. Unlike reports, goals get no cross-service linkage — current_amount is manual progress logging the user updates via PUT ("I moved $500 into savings this month"). It's never derived from expense data.

A subtle bug worth learning from PUT is a full-replace and is also the only way to log progress. An early version re-validated "target_date must be in the future" against the resent date even when the caller wasn't changing it — so once a goal's due date passed, it was permanently locked out of all further updates (including logging progress). Fixed to only reject a target_date that's both changed and in the past.

The computation, step by step

  1. List the caller's budgets from budget-service's own Mongo.
  2. Resolve category name → id. For each budget, budget-service calls expense-service GET /api/v1/categories and matches the budget's category name case-insensitively. No match → actual = 0 (not an error; the user just hasn't logged anything there yet).
  3. Sum the actual spend. It calls GET /api/v1/transactions?category=<id>&from=&to=&page_size=100, paging up to a safety cap of 50 pages (5,000 tx), summing amount where type == "expense". The type filter is done client-side in budget-service because expense-service has no server-side type filter — a known wrinkle worked around from the caller's side.
  4. Build the row: {category, period, budgeted, actual, remaining: budgeted − actual}, accumulating total_budgeted / total_actual.
  5. If over budget, fire an overspend notification (details below).

How the cross-service call is wired (and why it's testable)

The HTTP call lives in internal/client/expense_client.go, which implements a domain.ExpenseClient interface. The report service depends only on that interface — Dependency Inversion — so unit tests inject a fake and never stand up a real expense-service. The call forwards the caller's X-User-Id exactly as the gateway would (no JWT — it's an internal-network call using the same trust model as RequireIdentity).

The overspend notification — a documented trade-off

When a category is over budget, budget-service calls notification-service to create a visible in-app alert. This means a GET request has a side effect (creating a notification, mutating a budget field) — which is not pure REST. It exists only because Finora has no event bus yet; Phase 7 replaces it with a real "overspend event" published when the triggering transaction is created.

  • Dedup rule: a hidden LastNotifiedAt *time.Time on the budget stores the report period's from boundary that was last notified for — not a wall-clock time. A budget notifies only if LastNotifiedAt == nil or it doesn't exactly equal the current from. So reloading the same range doesn't re-notify, but viewing a different period does.
  • Why exact-match, not "notified after": an earlier version compared as a time ordering and broke for out-of-order queries — a user notified for the current month who then opened an older, never-viewed over-budget month had that legitimate first alert wrongly suppressed. Fixed to exact-period-match, with a regression test.
  • Failure is swallowed: if notification-service is unreachable, the error is logged and the report still returns 200 — a notification hiccup must not break a working read.
  • Known race (accepted): two concurrent first-time Summary calls for the same period could both notify once (no atomic check-and-set). Low consequence, narrow window, replaced wholesale by Phase 7 — not worth locking machinery today.

Feature · Notifications

A straightforward owner-scoped feed with two entry points that share one ownership model. A human lists/marks-read via the gateway; budget-service creates overspend alerts by forwarding the user's X-User-Id. The list paginates and supports ?unread_only=true, backed by a compound (user_id, read) index. On create, the service also invokes EmailSender.Send as a best-effort side effect — today a structured-log stub, swappable for real SMTP behind the interface without touching callers. The frontend surfaces this as a Notifications page plus a sidebar unread-count badge — because "a visible notification" needed an actual UI surface, not just an endpoint.

Feature · Profile & settings

In user-service. Profile: GET/PUT /users/me — you can edit your name (trimmed, 1–100 chars); email is read-only. Settings: GET/PUT /users/me/settings — currency (validated as a 3-letter uppercase code via a lightweight regex, deliberately not a full ISO-4217 table) and timezone (validated by actually calling time.LoadLocation).

A real production bug the settings page uncovered user-service's Alpine base image shipped without the tzdata package, so inside the container time.LoadLocation could only ever resolve "UTC" — every genuinely valid IANA zone (e.g. Europe/London) was rejected with the same 400 a garbage string gets. Invisible to go test because the host machine has tzdata. Fixed by adding tzdata in the Dockerfile. Lesson: validation that depends on OS data must be tested in the real runtime image, not just on a dev host.

15 · The data model

One MongoDB instance per service, never shared. Each service is only ever handed its own *_MONGO_URI. Isolation is physical, so a slow query or crash in one database can't touch another, and each maps 1:1 onto its own Kubernetes StatefulSet later.

16 · Cross-cutting concerns

Health probes (Kubernetes-shaped)

Every service exposes three endpoints via shared/health, following K8s probe conventions:

GET /liveAlways 200 if the process is up. Liveness never depends on downstream state (a Mongo blip must not get the pod killed).
GET /ready200 only if the Mongo ping succeeds, else 503. Readiness gates traffic. (The gateway owns no data, so its /ready is liveness-only.)
GET /healthRicher human/dashboard aggregate of the checks.

Structured logging & request tracing

middleware.RequestID ensures every request carries an X-Request-Id (generated if absent), echoed on the response and stamped into every log line. middleware.Logging emits one JSON line per request (method, path, status, latency, request_id), skipping the noisy health-probe paths. That single id ties a request together across all services — the foundation for the Phase-8 OpenTelemetry seam.

Rate limiting (gateway only, Phase 6)

A per-client-IP token bucket (golang.org/x/time/rate) in the gateway's chain after CORS, configured via RATE_LIMIT_REQUESTS_PER_SECOND/RATE_LIMIT_BURST (default 10/s, burst 20). Over-limit → 429 RATE_LIMITED. Deliberately in-memory, not Redis (single gateway instance today; Redis is the right answer only once there are multiple replicas). It fails open: a zero/unset config disables limiting rather than rejecting 100% of traffic — an unconfigured limiter must never look like an outage.

Configuration (12-factor)

No service hardcodes config. Everything is read from env vars via shared/config, enumerated in .env.example. Secrets and Mongo URIs use MustGetEnv (fail-fast at boot). This env-var-only shape maps cleanly onto Kubernetes ConfigMaps (non-secret) and Secrets (JWT secrets, credentials).

Graceful shutdown

shared/server.Run listens for SIGINT/SIGTERM and drains in-flight requests for up to SHUTDOWN_TIMEOUT before exiting — so a Kubernetes rollout/eviction doesn't drop live requests.

OpenAPI served live (Phase 6)

Every service serves its own spec at GET /openapi.yaml (read from disk at startup via shared/openapidoc; a missing file logs a warning and 404s rather than crashing). Each Dockerfile copies the spec into the final image.

17 · The frontend

Next.js (App Router, TypeScript). It talks only to the gateway, never to a service directly. Two files carry the whole integration story:

lib/api.ts — the fetch wrapper

  • Prefixes requests with NEXT_PUBLIC_API_BASE_URL and attaches Authorization: Bearer <access_token> from localStorage.
  • Unwraps the {success, data, error, request_id} envelope; throws a typed ApiError on failure.
  • Silent refresh on 401: exactly one attempt — on a 401 it calls /auth/refresh, and if that succeeds retries the original request once; if it fails, clears tokens and hard-redirects to /login. Concurrent 401s are de-duplicated so only one refresh fires.

lib/auth-context.tsx — client auth state

A React context that tracks "is there a token" (checked post-mount to avoid SSR mismatch) and exposes login/logout. Route protection for /dashboard/* is a client-side effect today.

Known Phase-0 simplification Tokens live in localStorage, which is readable by any script on the page — so an XSS could exfiltrate the 7-day refresh token. This is acknowledged in-code with a plan to move to httpOnly cookies set by Next.js route handlers. See §19.

Design system (the visual constitution)

architecture/frontend-design-system.md plays the same role for the UI that CLAUDE.md plays for the backend: flat, one accent color (violet), status color (green/amber/red) used only for financial polarity and never as decoration. Deliberately no UI-kit, icon library, or charting library — hand-rolled Tailwind primitives, ~14 inline-SVG icons, and a hand-built bullet chart for budget-vs-actual — each rejected for the same reason: a dependency this app's surface area doesn't justify. Money is always rendered with tabular-nums.

18 · Build & deploy wiring

Go modules: replace today, go.work supersedes it

Each service has its own go.mod with a replace github.com/finora/shared => ../../shared directive, so it builds standalone (critical for isolated Docker stages and single-service checkouts). A root go.work ties everything together for local dev (one go build ./..., consistent gopls, no version drift). The replace stays as the fallback because go.work is never used inside Docker builds.

Docker build context is the repo root

Every service's Dockerfile must COPY both shared/ and its own directory, so the build context is the repository root, not the service folder:

docker build -f services/user-service/Dockerfile .   # run from repo root

docker-compose.yml encodes this with context: . + a service-specific dockerfile: path. Images are multi-stage: a golang:1.21-alpine builder produces a static CGO_ENABLED=0 binary, copied into a minimal alpine runtime that runs as a non-root user with a health check. (user-service additionally installs tzdata — see Profile & settings.)

The local topology

docker compose up brings up 4 Mongo containers + 4 services + the gateway + the frontend, wired by health-check depends_on so nothing starts before its dependency is ready. Mongo log noise is redirected to a file inside the data volume (not stdout) so docker compose logs stays readable.

CI (Phase 6)

.github/workflows/ci.yml runs three jobs: go-unit (gofmt + vet + build + test, matrixed per service, fakes only), go-integration (real mongo:7 via testcontainers-go, build-tagged so it's opt-in), and frontend (build + lint). It's configured to run on PR-merge to main, not every push.

19 · Security posture (read before production)

Finora was built for local development, and the application code shows real security discipline: bcrypt hashing, refresh-token rotation with theft detection, hashed token storage, strict per-user data scoping, no password-hash leakage, no injection surface, and enumeration-resistant auth. The gaps are in the platform posture. The full catalogue lives in security/security_analysis.md; the headline items:

SeverityFinding
CriticalBackend services trust X-User-Id with no auth, and their ports are published to the host → a forged header bypasses auth entirely if exposed.
CriticalJWT secrets default to committed placeholder strings (dev-…-change-me); since HS256 is symmetric, knowing the secret forges any user's token.
HighMongoDB runs with no authentication; no TLS anywhere; no rate-limit was present pre-Phase-6 and there's still no account lockout on login.
MediumJWT algorithm not pinned; tokens in localStorage; no request body-size limits / server timeouts; Gin in debug mode; no security response headers.

Verdict: the app logic would pass a review; the surrounding platform (network isolation, secrets, transport, DB auth) is at local-dev maturity. Network isolation and real secrets are hard blockers before any production exposure. See the full report for the prioritized remediation order.
