An infrastructure critique of the five-service fleet, its data tier, its event bus, and its delivery pipeline — read against the requirements of high-throughput, low-latency operation.

§Verdict & headline numbers

The application architecture is genuinely good. Clean Architecture is real here, not aspirational: domain layers have no framework imports, every cross-cutting concern lives in one place in shared/, and the trade-offs are documented in the code where a reader will actually find them. That matters enormously for this review, because it means almost every problem below is fixable in one file rather than five.

The infrastructure is not ready for volume, and the gap is not incremental. It is currently a single-instance-of-everything system: one gateway, one replica per service, one standalone MongoDB per service with no authentication and no failover, one NATS node with a single-replica stream, no Kubernetes manifests beyond a namespace and one database Deployment, no metrics, and no traces. Under load it will not degrade gracefully; it will hit three hard ceilings — an internal request-amplification cascade, a connection-pool default, and an unbounded-timeout HTTP server — and fall over.

The most consequential finding is not any single misconfiguration. It is that a single user action fans out into tens of internal requests, and nothing in the system can currently observe that happening. Fixing that one design, plus roughly forty lines of connection and timeout configuration, is worth more than every other item in this document combined.

2 Idle connections per backend Go's DefaultTransport default, inherited unchanged by the gateway's reverse proxies.
0 Server timeouts set Read, ReadHeader, Write and Idle are all unset — that is, infinite — on every service.
0 Metrics or traces No /metrics, no OpenTelemetry, no request-id propagation across the two most expensive hops.
Read this caveat first

Every number in this document is derived from reading code, not from measuring a running system — because the system cannot currently be measured (see F13). They are order-of-magnitude estimates intended to rank work, not to be quoted as benchmarks. The first deliverable on the roadmap is not a fix, it is instrumentation. Ship metrics and traces first, then re-derive these numbers from real percentiles, then fix in the order the data says.

§On "zero latency"

There is no such thing, and chasing it produces worse systems than chasing a budget. Latency is a physical quantity with a floor set by distance and by the number of sequential hops on the critical path. Intra-availability-zone round trips are roughly 0.3–0.7 ms; cross-AZ is roughly 1–2 ms; cross-region is 30–70 ms and no amount of code changes that.

That physics is exactly why F01 is the headline finding. A design that makes 32 sequential internal round trips to serve one write costs at minimum 10–30 ms of pure network time even if every service and every database were infinitely fast. You cannot optimise your way out of a chatty design; you can only make it less chatty. Removing hops from the critical path is the only latency work that compounds.

The useful replacement for "zero latency" is a latency budget: a stated p99 per route class, an error budget that permits some violation, and an alert when the budget burns faster than it refills. A proposal is in Proposed SLOs. Everything in this review is ultimately in service of being able to state and defend such a budget.

§What is already right

A review that only lists faults misleads about where the work should go. These are load-bearing strengths, and several of them are why the remediation below is cheap:

  • The shared/ module is a genuine chokepoint for cross-cutting fixes. Connection pooling, timeouts, metrics, and tracing can each be added in one file and inherited by all five services. Very few codebases of this age have that.
  • Database-per-service is enforced physically, not by convention — separate containers, separate URIs. That is the precondition for ever scaling the services independently, and it has not been compromised anywhere.
  • The transactional outbox exists at all, with its non-atomicity documented honestly rather than papered over. Most systems this size publish events inline and lose them silently.
  • Durable JetStream consumers with explicit acks and a bounded MaxDeliver — the right primitives, even where the surrounding configuration needs work.
  • The /live · /ready · /health trio is correct: liveness genuinely does not depend on downstream state, readiness genuinely pings Mongo. That distinction is wrong in most codebases and it is right here.
  • Structured JSON logging with a propagated request id, and health-probe paths excluded from logs. Good instincts; it needs extending, not replacing.
  • Graceful shutdown on SIGTERM, non-root container users, multi-stage builds, idempotent index creation at boot, and a real testcontainers integration tier separate from unit tests.
  • Configuration is entirely environment-driven. The ConfigMap/Secret split is a translation, not a redesign.

1. The write-amplification cascade

The single most important thing in this document. Everything else is configuration; this is design.

F01 One transaction write generates tens of internal requests Critical

expense-service/internal/service/transaction_service.go → shared/outbox → NATS → budget-service/internal/service/overspend_service.go → budget-service/internal/client/expense_client.go

Trace the path of a single POST /api/v1/transactions:

  1. expense-service writes the transaction and enqueues finora.transaction.created to its outbox.
  2. The relay publishes it; budget-service's durable consumer picks it up.
  3. HandleTransactionCreated loads every budget the user owns and, for each one, calls SumExpensesByCategory.
  4. SumExpensesByCategory makes one GET /api/v1/categories call to resolve a category name to an id, then walks GET /api/v1/transactions page by page, up to 50 pages of 100, summing amounts client-side.

So the cost of one write is B × (1 + P) internal HTTP round trips, where B is the user's budget count and P is the number of transaction pages in that category and period. Each of those transaction-list calls additionally runs a CountDocuments over the full match set (F06) whose result is computed and thrown away, so the Mongo query count is roughly double the HTTP count.

Put numbers on it. A user with 8 budgets and ~250 transactions in the current period per category:

QuantityValueDerivation
Internal HTTP calls per write328 × (1 + 3)
Mongo queries per write~5624 finds + 24 discarded counts + 8 category finds
Documents decoded and discarded~2,40024 pages × 100 docs, to produce 8 floats
At 1,000 writes/min external533 internal RPS32,000 calls/min ÷ 60
Consumer throughput ceiling~15 events/s/replica32 calls × ~2 ms serial ≈ 65 ms per event

That last row is the operative constraint. The consumer handler is invoked serially, so budget-service processes roughly 15 transaction events per second per replica. At about 1,000 transactions per minute of ingest, event lag begins growing without bound — the queue depth rises, overspend alerts arrive minutes then hours late, and nothing in the system reports it (F13). This is the fleet's real write ceiling today, and it is two orders of magnitude below what "high RPM" implies.

The same code path also serves GET /api/v1/reports/summary synchronously, budget by budget, in a loop. A user with 12 budgets can trivially exceed three seconds of wall-clock latency on a page load, and there is no overall request deadline — only a 3-second timeout on each individual outbound call, of which there may be 48.

Remediation

Step 1 — collapse the fan-out to one call (days). Add an aggregation endpoint to expense-service and delete the pagination loop entirely:

// GET /api/v1/transactions/aggregate?group_by=category_id&from=&to=&type=expense
pipeline := mongo.Pipeline{
  {{"$match", bson.D{
      {"user_id", userID},
      {"type", "expense"},
      {"date", bson.D{{"$gte", from}, {"$lt", to}}},
  }}},
  {{"$group", bson.D{
      {"_id", "$category_id"},
      {"total", bson.D{{"$sum", "$amount"}}},
      {"count", bson.D{{"$sum", 1}}},
  }}},
}

With the index from F05 this is a single covered index scan with no documents crossing the wire. B × (1 + P) becomes 1, for any B and any P. The consumer's per-event cost drops from ~65 ms to ~2 ms, a roughly 30× throughput increase for a day of work. It also removes the silent truncation at 5,000 transactions (F21) — the aggregate is correct for any volume.

Step 2 — debounce (days). A user importing a CSV of 500 transactions currently triggers 500 recomputations of the same figures. Coalesce events per user over a short window (2–5 s) and recompute once. Trivially: a per-user timer map, or a JetStream work queue keyed by user with a deliberate delay.

Step 3 — eliminate the cross-service call (weeks). The event already carries user_id, category_id, amount, and date — everything needed to maintain a rolling (user_id, category_id, period) spend counter in budget-service's own database with a single $inc upsert. Overspend detection then becomes an O(1) local read with zero cross-service traffic. Keep the aggregation endpoint as the reconciliation path: recompute from source on a schedule and correct drift, which is the standard pattern for derived financial counters.

2. Edge & gateway

The gateway is the only public entrypoint. Every ceiling here is a ceiling for the whole product.

F02 Reverse proxies inherit Go's 2-idle-connection default Critical

services/gateway/internal/proxy/proxy.go, services/budget-service/internal/client/expense_client.go

httputil.NewSingleHostReverseProxy leaves Transport nil, which means http.DefaultTransport, which sets MaxIdleConnsPerHost: 2. Likewise NewExpenseHTTPClient builds &http.Client{} — same default, on the single hottest internal path in the fleet.

The consequence is not slow — it is catastrophic and it arrives suddenly. Beyond two concurrent requests to a backend, every additional request opens a fresh TCP connection, and on completion that connection cannot be returned to the idle pool because the pool is full, so it is closed. The gateway, as the side initiating the close, holds each socket in TIME_WAIT for 60 seconds.

The arithmetic

At 1,000 RPS to one backend, roughly 998 connections per second are created and destroyed. Sustained, that is ~60,000 sockets in TIME_WAIT against a single destination. The default Linux ephemeral port range is about 28,000 ports. You exhaust the port space and begin returning connect: cannot assign requested address — a hard, total failure of the gateway that looks like a network problem and is actually a two-line configuration default.

Additional costs before that point: a TCP handshake (and, once TLS is introduced between hops, a TLS handshake) added to every single request's latency; kernel memory per socket; and connection-tracking table pressure on any NAT or CNI in the path.

Remediation — under an hour, highest leverage in the repository 
func newTransport() *http.Transport {
    return &http.Transport{
        Proxy: http.ProxyFromEnvironment,
        DialContext: (&net.Dialer{
            Timeout:   3 * time.Second,
            KeepAlive: 30 * time.Second,
        }).DialContext,
        ForceAttemptHTTP2:     true,
        MaxIdleConns:          512,
        MaxIdleConnsPerHost:   256,  // the fix
        MaxConnsPerHost:       512,  // bulkhead: bounds blast radius
        IdleConnTimeout:       90 * time.Second,
        TLSHandshakeTimeout:   3 * time.Second,
        ResponseHeaderTimeout: 10 * time.Second,
        ExpectContinueTimeout: 1 * time.Second,
    }
}

Assign it to rp.Transport in proxy.New and to the http.Client in expense_client.go. Size MaxIdleConnsPerHost to your target per-pod concurrency; MaxConnsPerHost is the bulkhead that stops one slow backend from consuming every file descriptor the pod has.

F07 Rate limiting is per-instance, lock-contended, and bypassable High

shared/middleware/ratelimit.go, services/gateway/internal/router/router.go

Three independent problems in one component:

It can be bypassed outright. gin.New() trusts all proxies by default, so c.ClientIP() honours a client-supplied X-Forwarded-For. An attacker sending a different random value per request gets a fresh, full token bucket every time — the limiter enforces nothing. Worse, it inverts: each spoofed IP allocates a map entry retained for three minutes, so the very component meant to prevent resource exhaustion becomes an unbounded memory-growth vector. Its own doc comment identifies unbounded map growth as the thing to prevent; the trusted-proxy default reopens it.

It serialises all traffic through one mutex. Every request takes a single global sync.Mutex, and the 60-second sweeper takes the same lock while iterating the entire map. With a few hundred thousand tracked IPs, that sweep is a multi-millisecond stop-the-world pause applied to all inbound traffic, once a minute — a periodic p99 spike that will be very hard to diagnose without traces.

It does not survive horizontal scaling. The doc comment is candid that this is single-instance-only and that scaling out is the trigger to revisit. That trigger has arrived: with N replicas a client's effective limit is N × the configured rate, and it silently changes every time the HPA scales.

Remediation

Now (minutes): r.SetTrustedProxies([]string{ingressCIDR}), or r.TrustedPlatform when behind a cloud LB that sets a trustworthy header. This is a correctness fix, not an optimisation.

Next (hours): shard the visitor map across ~256 mutexes keyed by a hash of the IP, and sweep one shard per tick rather than the whole map at once. Contention drops by two orders of magnitude and the sweep pause becomes invisible.

Then (days): two-tier limiting, which is what large systems actually run. Coarse per-IP limits at the edge — ingress-nginx, Envoy, or the CDN/WAF, where they cost you nothing and stop traffic before it reaches your compute. Fine-grained per-user and per-endpoint quotas in the app, backed by Redis with a GCRA or sliding-window script so the limit is fleet-wide and independent of replica count. Keep the in-process limiter as a local safety valve for when Redis is unavailable — fail open, exactly as it does today.

F22 No idempotency keys on financial writes Medium

expense-service/internal/handler/transaction_handler.go, frontend/lib/api.ts

POST /api/v1/transactions has no idempotency mechanism. The frontend wrapper retries once after a silent token refresh; browsers, mobile clients, and any future SDK retry on network errors. A retry that lands after the original succeeded but before the response arrived double-books a financial record. This is not a scale-only problem, but scale makes it routine: the rate of ambiguous timeouts is proportional to traffic, and at high RPM you will be creating duplicate transactions continuously.

Remediation

Accept an Idempotency-Key header on all non-GET routes. Store (user_id, key) → (status, response_body) with a unique index and a 24-hour TTL; on a duplicate key, replay the stored response rather than re-executing. This is the standard payments-API contract and it also gives the outbox a natural dedup identity. The gateway can enforce the header's presence centrally.

3. Service runtime

Shared across all five services via shared/server — which means one file fixes all five.

F03 Every HTTP server has infinite timeouts Critical

shared/server/server.go

server.Run constructs &http.Server{Addr: addr, Handler: handler}. ReadTimeout, ReadHeaderTimeout, WriteTimeout, and IdleTimeout all default to zero, which in Go means no limit. Three consequences:

  • Slowloris. An attacker opens thousands of connections and dribbles headers a byte at a time. Each holds a goroutine, a file descriptor, and a read buffer indefinitely. Neither the rate limiter nor the body-size limiter helps: the request never completes, so it is never counted and its body is never read. A single host can take the gateway down with negligible bandwidth.
  • Head-of-line resource leaks. A backend that accepts a connection and then hangs holds a gateway goroutine forever. With F02's connection churn this compounds fast.
  • Unbounded growth under load. Idle keep-alive connections are never reaped. Connection count only rises, until the file-descriptor limit is hit and accept() fails — at which point the service is fully down and its /live probe may well still pass, so Kubernetes will not even restart it.
Remediation — under an hour, applies to all five services at once 
srv := &http.Server{
    Addr:              addr,
    Handler:           handler,
    ReadHeaderTimeout: 5 * time.Second,   // kills Slowloris outright
    ReadTimeout:       15 * time.Second,
    WriteTimeout:      30 * time.Second,
    IdleTimeout:       120 * time.Second,
    MaxHeaderBytes:    1 << 20,
    ErrorLog:          slog.NewLogLogger(log.Handler(), slog.LevelError),
}

ReadHeaderTimeout alone closes the Slowloris vector and is the single highest-value line. Set WriteTimeout above the slowest legitimate response — today that is the reports endpoint, which is unbounded until F01 is fixed, so fix F01 first or the timeout will cut off real users. The durable pattern is a generous WriteTimeout plus per-route context.WithTimeout deadlines that propagate into Mongo and outbound calls, so a slow request is cancelled all the way down rather than merely disconnected at the top.

F10 Shutdown does not sequence with endpoint removal High

shared/server/server.go, all cmd/server/main.go

On SIGTERM the server calls srv.Shutdown immediately. In Kubernetes, SIGTERM and Endpoint removal are dispatched concurrently and endpoint propagation to every kube-proxy and ingress controller is eventually consistent — typically 1–5 seconds. During that window the pod is still receiving traffic while actively refusing it. Every rolling deploy produces a burst of 502s, and the burst scales with replica count and request rate, so it gets worse exactly as you scale.

Nothing flips /ready to failing first, so load balancers have no signal to drain against. Separately, the outbox relay and NATS consumer goroutines are cancelled after server.Run returns; in-flight message handlers are not waited on, so a handler can be cut mid-publish (recoverable — the message is redelivered — but it means shutdown is not clean).

Remediation

Implement the standard drain sequence in shared/server:

  1. On SIGTERM, atomically flip a ready flag to false so /ready starts returning 503, but keep serving traffic.
  2. Sleep readinessProbe.periodSeconds × failureThreshold plus a margin — long enough for every load balancer to observe the failure and remove the endpoint.
  3. Then call srv.Shutdown to drain in-flight requests.
  4. Cancel background contexts and wait on a sync.WaitGroup for consumers and relays.

Pair it with a pod spec preStop: exec: ["sleep", "5"] and terminationGracePeriodSeconds comfortably greater than preStop + drain + shutdown timeout. Verified correct, rollouts become invisible to users — which is the precondition for deploying frequently, which is the precondition for everything else on this roadmap.

F20 Gin runs in debug mode in production Low

all internal/router/router.go; gin.SetMode appears only in _test.go files

Gin defaults to debug mode. Nothing in any Dockerfile or in docker-compose.yml sets GIN_MODE=release, so every container runs with debug route dumping and extra per-request bookkeeping. Small, but free to fix, and debug-mode output on startup is noise in the log pipeline you are about to build.

Remediation

gin.SetMode(gin.ReleaseMode) in each main.go (or ENV GIN_MODE=release in the Dockerfiles — prefer the code, since it cannot be lost during a manifest edit). Take the trusted-proxy fix from F07 at the same time; both are one line in the same place.

F21 Serial health checks, and reports that truncate silently Low

shared/health/health.go, budget-service/internal/client/expense_client.go

runChecks creates one 2-second context and runs every checker sequentially against it. Services with both a Mongo and a NATS checker share that single budget, so a slow Mongo consumes the time allotted to the NATS check and readiness reports the wrong dependency as broken. Checks should run concurrently, each with its own deadline, with results aggregated. At high pod counts, also cache the result for ~1 second so probe traffic does not itself become a meaningful load on the database.

Separately, maxReportPages = 50 caps SumExpensesByCategory at 5,000 transactions and then returns a number that is simply wrong, with no error and no flag. In a personal-finance product, a silently under-reported spend total is worse than a failed request. The F01 aggregation fix removes the limit and the failure mode together.

4. Data tier

Four standalone MongoDB instances, no authentication, no failover, no tuning.

F05 The index cannot satisfy the sort on the hottest query High

expense-service/internal/repository/mongo.go, mongo_transaction.go

The transactions index is {user_id: 1, account_id: 1, date: 1}. The list query filters on user_id (with account_id optional) and always sorts {date: -1}. When no account filter is supplied — the default dashboard view, and therefore the most-executed query in the product — MongoDB can use user_id as an index prefix for the match but cannot use the index to provide sorted order, because account_id sits between the equality field and the sort field.

The result is a blocking in-memory SORT stage over the user's entire matched transaction set on every page request, including page 1. Two consequences:

  • Cost is O(n log n) in the user's total transaction count, not in page size. Latency degrades as a user's history grows, which is precisely the wrong direction for a finance product where power users are your best users.
  • It eventually fails outright. MongoDB aborts a blocking sort exceeding 32 MB without allowDiskUse. At roughly 200 bytes per document that is around 160,000 transactions for one user — reachable through the CSV importer. The endpoint then returns 500 for that user, permanently, until someone notices.
Remediation — minutes 
// ESR: Equality fields, then Sort fields, then Range fields.
{user_id: 1, date: -1}                    // default list + date range
{user_id: 1, account_id: 1, date: -1}     // account-filtered list
{user_id: 1, category_id: 1, date: -1}    // category-filtered + the F01 aggregate

Sort direction matters: MongoDB can walk an index backwards, so date: -1 and date: 1 are interchangeable for a single-field sort, but keeping the declared direction aligned with the query's makes intent obvious to the next reader. Add an explain("executionStats") assertion to the existing testcontainers integration tests asserting IXSCAN and no SORT stage — that turns a class of regression into a test failure rather than a production incident. This repository already has the integration-test tier to host it.

F06 Offset pagination with a full count on every page High

expense-service/internal/repository/mongo_transaction.go, notification-service/internal/repository/mongo_notification.go

Both list endpoints do the same two things per request, and both scale with data rather than page size:

  • CountDocuments runs a full aggregation count over the entire match set to produce a total. That is O(matched documents) — for a user with 100,000 transactions, every single page request scans 100,000 index entries to render "of 100,000".
  • skip(N) is O(N): the server walks and discards N entries before returning any. Page 500 discards 10,000 entries; deep pagination degrades linearly and predictably.

Under F01's cascade this is multiplied: each of the up-to-50 internal page fetches pays the full count again, computing and discarding the same number 50 times per budget.

Remediation

Keyset (seek) pagination. Replace skip with a cursor on the sort key:

// cursor encodes the last row's (date, _id) — _id breaks ties deterministically
q["$or"] = bson.A{
    bson.M{"date": bson.M{"$lt": cursorDate}},
    bson.M{"date": cursorDate, "_id": bson.M{"$lt": cursorID}},
}
opts := options.Find().SetSort(bson.D{{"date", -1}, {"_id", -1}}).SetLimit(pageSize + 1)
// fetch pageSize+1: the extra row tells you has_more without a count

Every page then costs the same regardless of depth, and the flat latency curve is what makes a p99 target defensible. Return an opaque base64 next_cursor in the envelope; keep page/page_size accepted-but-deprecated for one release so the frontend can migrate.

Drop the exact total. Serve estimatedDocumentCount, or a periodically cached per-user count, or nothing at all. Every product operating at scale shows "1–20 of many" precisely because an exact count is the most expensive thing on the page and the least valuable thing on it.

F11 MongoDB is standalone, unauthenticated, host-exposed, and untuned High

docker-compose.yml, shared/mongox/mongox.go, infrastructure/kubernetes/mongo-user/

Topology

Every Mongo container runs standalone — no --replSet. That single decision costs four capabilities simultaneously:

  • No failover. Any restart, node loss, or disk problem is a total outage of that service's data with no automatic recovery. There is one copy of the data and it is on one machine.
  • No multi-document transactions — which is exactly why shared/outbox cannot be atomic. That limitation is honestly documented as a deliberate trade-off, and the documentation is right that fixing it is an infrastructure change rather than a code change. This is that infrastructure change.
  • No change streams, which would otherwise be the cleanest possible outbox implementation — tail the oplog instead of polling (F04).
  • No read scaling. Secondaries with readPreference=secondaryPreferred are the cheapest available capacity increase for read-heavy endpoints like reports.

Access control

Unauthenticated and published

No --auth, no credentials in any URI, and ports: ["27017:27017"] (through :27020) publishes all four databases on the host. Anything that can reach the host — or, in Kubernetes without NetworkPolicies, anything running anywhere in the cluster — has unauthenticated administrative access to every financial record in the system. The compose comment explains the port mapping is for MongoDB Compass, which is a reasonable local-development want served by kubectl port-forward or a compose override file, not by publishing the port by default.

Driver configuration

mongox.Connect applies the URI and nothing else. Unset, and worth setting:

Remediation

Local: run each Mongo as a single-member replica set (--replSet rs0 with an init container running rs.initiate()). One flag, and it unlocks transactions and change streams immediately — the outbox becomes genuinely atomic with no application redesign.

Kubernetes: a StatefulSet with three members and a per-member PersistentVolumeClaim, or the MongoDB Community Operator, which handles replica-set membership, TLS, and rolling upgrades for you. A managed service is the other legitimate answer, and for a system whose purpose includes learning to operate infrastructure, the operator is the more instructive choice.

Everywhere: enable --auth with per-service credentials from a Secret, enable TLS in transit, remove the published host ports from the default compose file, and add a restore drill — a backup you have never restored is a hypothesis, not a backup.

F12 Money is stored and summed as float64 High

expense-service/internal/domain/transaction.go, budget-service/internal/domain/budget.go, internal/client/expense_client.go

Amounts are float64 throughout — domain, BSON, and JSON. IEEE-754 binary floating point cannot represent 0.10 exactly, and SumExpensesByCategory accumulates total += tx.Amount across up to 5,000 values, compounding representation error with every addition. The overspend decision is then b.Amount - actual < 0 — a threshold comparison decided by that accumulated error.

At small volume this is invisible. At scale it produces alerts that fire on the wrong side of a boundary, totals that disagree between the report endpoint and the overspend check, and reconciliation discrepancies that cannot be explained because they are not deterministic. It is listed here rather than dismissed as an application concern because it is the class of defect that cannot be retrofitted cheaply once there is production data — every fix requires a migration of every historical record.

Remediation

Store minor units as int64 (cents), or MongoDB's Decimal128 if multi-currency precision beyond two places is anticipated. Do the summation in the database with $sum rather than in Go — which the F01 aggregation pipeline already does. Keep the JSON wire format a decimal string, not a JSON number, so JavaScript's own float64 does not reintroduce the problem in the browser. Do this before there is production data; the cost rises monotonically from here.

F16 No caching layer of any kind Medium

fleet-wide

Every read reaches MongoDB. There is no in-process cache, no Redis, no HTTP cache headers, no ETag, no CDN. Some of what is being re-fetched is close to static: findCategoryIDByName fetches a user's entire category list on every single SumExpensesByCategory call — which, under F01, is once per budget per transaction event.

plan.md defers Redis until there is a legitimate reason to introduce it, which is the right default posture. F01 is that reason, and it arrives with measurements attached.

Remediation, cheapest first
  • golang.org/x/sync/singleflight + a small TTL LRU for the category lookup. In-process, no new infrastructure, and it collapses the thundering herd of identical concurrent lookups that a CSV import produces.
  • Cache-Control and ETag on GET responses. Free bandwidth and latency savings from the browser, and the precondition for ever putting a CDN in front of the API.
  • Redis once multi-replica: shared caches, the distributed rate limiter from F07, and idempotency-key storage from F22. One dependency serving three needs is a much easier justification than one serving one.

Cache invalidation is the real design work. Prefer short TTLs over clever invalidation: a 30-second stale category list is harmless and needs no invalidation logic at all, whereas an event-driven invalidation scheme is a new distributed-systems problem you would be choosing to own.

5. Event bus & outbox

The right pattern, wired with defaults that do not survive multiple replicas.

F04 The outbox relay is not safe to run in more than one replica Critical

shared/outbox/outbox.go, expense-service and budget-service cmd/server/main.go

Each service starts a relay goroutine at boot. That is correct for one replica and incorrect for two. Four distinct problems:

No claim, so every replica publishes every event

RelayOnce runs Find({published_at: nil}), publishes, then marks. With N replicas, all N read the same unpublished set and all N publish it. Both publishers do set a JetStream MsgID (tx.ID, and budget_id:period_start), and JetStream collapses duplicates within its dedup window — so this is bounded rather than unbounded, which is genuinely good design and worth crediting. But it only holds inside the window. Anything republished after the default two minutes — a backlog draining after a NATS outage, or an event whose UpdateByID marking failed — is delivered again for real. And even where dedup saves correctness, you are still paying N× the publish work and N× the Mongo write load, forever.

Unbounded scan

The find has no limit and no sort. After any outage the entire backlog is processed in a single serial pass holding one cursor open — and MongoDB times out an idle cursor after 10 minutes, so a large enough backlog fails with CursorNotFound partway through and restarts from the beginning on the next tick. The system's recovery behaviour gets worse the more there is to recover, which is the defining characteristic of an outage that does not end.

Serial publishes

One publish per round trip, sequentially. This is the throughput ceiling of the entire write path, and it does not improve with hardware.

Nothing reaps published events

outbox_events grows without bound; published rows are never deleted. Storage, backup time, and restore time all grow monotonically forever. The index on {published_at: 1} also indexes every published row, when only the unpublished ones are ever queried.

Remediation — a day, and it unblocks horizontal scaling 
// 1. Partial index: only unpublished rows are indexed at all.
//    The index stays small permanently, no matter how many events ship.
mongo.IndexModel{
    Keys: bson.D{{"published_at", 1}, {"created_at", 1}},
    Options: options.Index().SetPartialFilterExpression(
        bson.M{"published_at": bson.M{"$eq": nil}}),
}

// 2. TTL index reaps published rows after 72h (post-mortem headroom).
mongo.IndexModel{
    Keys:    bson.D{{"published_at", 1}},
    Options: options.Index().SetExpireAfterSeconds(72 * 3600),
}

// 3. Claim before publishing, so replicas cannot collide.
res := col.FindOneAndUpdate(ctx,
    bson.M{"published_at": nil, "locked_until": bson.M{"$lt": now}},
    bson.M{"$set": bson.M{"locked_until": now.Add(30 * time.Second), "locked_by": podName}},
    options.FindOneAndUpdate().SetSort(bson.D{{"created_at", 1}}))

// 4. Bounded batch + bounded concurrency, not one-at-a-time.
//    Fetch 500, publish with a pool of 32, mark with one BulkWrite.

The better long-term answer: once the replica set from F11 exists, replace polling with a MongoDB change stream on the outbox collection. Publish latency drops from "up to OUTBOX_RELAY_INTERVAL" (2 seconds today, a floor on every downstream notification) to milliseconds, the poll load disappears entirely, and resume tokens give you exactly the restart semantics the current design is trying to approximate with a ticker.

F08 The JetStream stream is a single point of data loss High

shared/eventbus/eventbus.go, all three cmd/server/main.go, docker-compose.yml

EnsureStream sets a name, subjects, LimitsPolicy, and a 30-day MaxAge. What it does not set matters more:

  • Replicas is unset — the stream is R=1. Combined with a single NATS container, losing that one node or its volume loses every unacknowledged financial event in flight. The whole reason JetStream was chosen over core NATS was durability; R=1 on a single node gives you persistence across a restart but not durability against a node loss.
  • MaxBytes is unset. With LimitsPolicy and a 30-day age limit, the store grows until the volume is full, at which point publishes fail — the outbox backs up, Mongo's outbox collection grows (F04 has no reaping), and the failure cascades backwards into the write path.
  • Discard is unset, defaulting to DiscardOld: at a limit, JetStream silently deletes the oldest messages. For financial events, silently dropping the oldest is the worst available choice. DiscardNew fails the publish loudly instead, which the outbox is already built to retry.
  • One finora.> catch-all stream means every domain shares one retention policy, one storage budget, and one hot path. A burst on one subject consumes the headroom of every other.
  • All three services call CreateOrUpdateStream at boot. The doc comment argues that shared infrastructure should not have a single designated owner, which is a defensible instinct — but the mechanism is mutating, so whichever pod boots last silently rewrites the stream's configuration. During a rolling deploy where subject lists differ between old and new versions, the stream config flaps.
Remediation

Run NATS as a 3-node cluster and declare streams with Replicas: 3, explicit Storage: FileStorage, an explicit MaxBytes, and Discard: DiscardNew. Split into per-domain streams (FINORA_TRANSACTIONS, FINORA_BUDGETS) so retention and limits can differ and a hot subject cannot starve a cold one.

Move provisioning out of application startup into a Helm hook or a Kubernetes Job running the nats CLI, and have services verify the stream exists and fail fast if it does not, rather than mutating it. Stream topology is infrastructure; it belongs with the infrastructure, declared once, versioned, and reviewed.

F09 No backoff, no dead-letter — failed events are silently discarded High

shared/eventbus/eventbus.go

The consumer sets AckExplicitPolicy and MaxDeliver: 10, and on handler error calls a bare msg.Nak(). A bare Nak requests immediate redelivery. So when a dependency is down — expense-service unreachable, exactly the case F01's handler depends on — a message burns through all ten delivery attempts in milliseconds and is then dropped permanently, with no dead-letter queue, no alert, and no record. A budget-overspent notification the user should have received simply never exists, and nothing in the system knows.

The hot retry loop is separately damaging: during a downstream outage, the consumer spins at full speed against a failing dependency, adding load precisely when the system is least able to absorb it. That is a textbook retry storm, and it turns a partial outage into a total one.

Throughput is the other half. Messages are dispatched to the callback serially, so per-replica throughput is 1 / handler_latency. With F01's ~65 ms handler that is ~15 events/s/replica. Replicas do share load — they use the same durable name and therefore form a queue group, which is correct — but you are scaling pods to work around a design cost rather than removing it.

Remediation 
cons, err := stream.CreateOrUpdateConsumer(ctx, jetstream.ConsumerConfig{
    Durable:       durableName,
    AckPolicy:     jetstream.AckExplicitPolicy,
    FilterSubject: filterSubject,
    MaxDeliver:    10,
    AckWait:       30 * time.Second,          // > p99 handler latency
    BackOff: []time.Duration{                  // server-side exponential backoff
        1 * time.Second, 5 * time.Second, 15 * time.Second,
        30 * time.Second, 1 * time.Minute, 5 * time.Minute,
    },
    MaxAckPending: 256,                        // bounded in-flight window
})

Distinguish retryable from terminal in the handler contract: a network error should Nak with backoff; a permanently malformed payload should msg.Term() and be routed to a DLQ subject. Budget-service already gets this right for unmarshal failures — it acks and logs rather than retrying a payload that will never parse. Generalise that instinct into the shared Handler signature with a typed ErrTerminal.

Then consume the JetStream advisory $JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.> into a durable dead-letter store and alert on it. An event that exhausted its retries is an incident, not a log line. Finally, add bounded concurrency inside the handler dispatch — a worker pool of k with MaxAckPending sized above it — so throughput is not pinned to one message at a time.

6. Kubernetes & deployment

Honest framing: this is the least-built area, and it is explicitly a work in progress.

F18 Almost nothing exists yet, and the one manifest models a database as a Deployment Medium

infrastructure/kubernetes/

The directory contains a namespace and a mongo-user Deployment with replicas: 1, no PVC, no resources, no probes, and no securityContext. Its README is candid that this is a deliberate learning-order decision and that PVCs come later, so this is not drift — it is a stated position. The critique is about what the target needs to include, and about one modelling choice worth correcting before it is copied four more times.

Correct this before replicating it

A database belongs in a StatefulSet, not a Deployment. A Deployment's default RollingUpdate strategy starts the new pod before terminating the old one; once a PVC is attached, with a ReadWriteOnce volume the new pod simply cannot start (the deploy hangs), and with ReadWriteMany two mongod processes attempt to open the same data files, which corrupts them. StatefulSets give stable network identity, ordered rollout, and a volumeClaimTemplate that provisions one volume per replica — all three are prerequisites for a replica set. If you keep a Deployment for any stateful workload in the interim, set strategy: Recreate so the failure mode is downtime rather than corruption.

7. CI/CD & supply chain

The pipeline validates code after it has already landed, and never builds the artifact it ships.

F17 CI runs after merge and never builds an image Medium

.github/workflows/ci.yml

The trigger is pull_request: types: [closed] gated on merged == true. The workflow documents this as an explicit request and an accepted trade-off, and notes how to add a pre-merge gate later. Taking it on its own terms, here is what it costs at scale: there is no required status check possible, because a check that only runs post-merge can never gate a merge. Branch protection has nothing to enforce. main can be broken by any merge and stays broken until someone reads the notification. As contributor count and merge rate rise, mean-time-to-red-main rises with it.

What the pipeline never does at all:

MissingConsequence
Docker image buildNothing verifies the five Dockerfiles. A broken Dockerfile is discovered at deploy time, or by a person running compose.

Build reproducibility and image hygiene

  • Every base image is a floating tag — golang:1.21-alpine, alpine:3.19, mongo:7, nats:2-alpine, node:20-alpine. Two builds of the same commit can produce different binaries, and a base-image change lands unannounced. Pin by digest and let Renovate or Dependabot propose bumps as reviewable PRs.
  • Layer caching is defeated. Every Dockerfile does COPY shared/ ... then COPY services/x/ ... then RUN go mod download. Because the source is copied before the download, any source edit invalidates the dependency layer and re-downloads every module. Copying only go.mod/go.sum first cuts rebuild time dramatically.
  • No build flags. -trimpath -ldflags="-s -w" shrinks binaries and removes build-path leakage. No --mount=type=cache for the module and build caches.
  • Alpine as the runtime base ships a shell and a package manager into production. gcr.io/distroless/static or scratch is a smaller attack surface for a static CGO_ENABLED=0 binary. The one genuine exception is user-service, which needs tzdata — and distroless-static includes it, so even that is covered.
  • No .dockerignore at the repository root (the frontend has one). Every service build ships .git, the 108 KB plan.md, and any local node_modules into the build context.
Remediation

Split the pipeline in two, which the existing workflow comment already anticipates: a pre-merge workflow on pull_request running fmt, vet, lint, -race unit tests, integration tests, image builds, and scans — set as required status checks. A separate post-merge release workflow builds, signs, generates an SBOM, pushes by digest, and opens the deployment PR. Add a nightly govulncheck and a scheduled k6 run against a staging environment with percentiles published as a build artifact.

8. Security as an availability property

Scoped to the items that determine whether the system stays up and whether it can be multi-tenanted safely.

F14 X-User-Id is trusted with no enforcement that only the gateway sets it Medium

shared/middleware/identity.go, docker-compose.yml

RequireIdentity accepts any non-empty X-User-Id. The gateway correctly overwrites the header with the validated subject and never forwards a client-supplied one — that part is right. The problem is that nothing prevents reaching a backend service without going through the gateway.

In compose, ports 8081–8084 are published on the host, so curl -H 'X-User-Id: <any-user>' localhost:8082/api/v1/transactions returns another user's complete financial history with no token at all. In Kubernetes there are no NetworkPolicies, so any pod in the cluster can do the same. CLAUDE.md documents this as a deliberate trade-off revisited in Phase 9, so it is a known position rather than an oversight — but at scale the difference matters: it converts any single compromised workload anywhere in the cluster into a full customer-data breach, and it blocks multi-tenancy, partner traffic, and any compliance posture.

Remediation, in increasing order of cost
  1. Stop publishing backend ports in the default compose file. Move them to docker-compose.override.yml for local debugging. Minutes.
  2. Default-deny NetworkPolicy, allowing only gateway→service and service→its own database. Hours, and it makes the trust boundary a real one instead of a documented convention.
  3. Sign the identity assertion. Have the gateway mint a short-lived internal token (30 s, audience = target service) that the service verifies. Preserves "the gateway is the only validator of user tokens" while making the header unforgeable. Days.
  4. mTLS via a service mesh. Linkerd is the low-overhead choice and gives you cryptographic workload identity, plus per-hop golden metrics for free — which also happens to be a large slice of F13.

F15 Shared symmetric signing key, no rotation, no revocation Medium

shared/jwtx/jwtx.go, services/gateway/internal/authmw/authmw.go

  • HS256 with a shared secret. Gateway and user-service both hold JWT_ACCESS_SECRET. Anything that can read the gateway's environment can mint a valid token for any user. A verifier should never need the ability to sign.
  • No kid header, so rotating the secret is a flag-day: every token issued under the old key breaks the instant the new key is deployed.
  • No revocation. A stolen 15-minute access token is valid for 15 minutes with no kill switch. Refresh tokens are stored and revocable — good — but access tokens are not.
  • No jwt.WithValidMethods, no iss/aud validation. Low risk today given an HMAC-only key function, but algorithm pinning is one argument and costs nothing.
Remediation

Move to RS256 or EdDSA with a JWKS endpoint on user-service and a caching JWKS client in the gateway. The gateway then holds only public keys, rotation becomes a rolling operation with overlapping kids, and the architectural rule ("the gateway is the only JWT validator") is preserved intact. Add WithValidMethods, iss, and aud checks in the same change. For revocation, a small deny-list of jtis in Redis with a TTL equal to the access-token lifetime is sufficient and cheap.

9. Observability

The prerequisite for every other item in this document.

F13 No metrics, no traces, and correlation breaks at the two most expensive hops High

fleet-wide; shared/logger, shared/middleware, budget-service/internal/client/expense_client.go

Searching the entire repository for prometheus, otel, or metrics returns nothing. There is no /metrics endpoint, no OpenTelemetry, no tracing, no SLOs, and no alerting. Structured JSON logging with a request id exists and is well done — but logs alone cannot answer "what is my p99", "which dependency is slow", or "how many replicas do I need", and every one of those questions has to be answerable before any capacity decision can be made.

Two specific gaps make the existing correlation less useful than it looks:

  • The internal REST call does not propagate X-Request-Id. ExpenseHTTPClient.doGet sets only X-User-Id. The correlation chain therefore breaks at exactly the hop generating 97% of internal traffic (F01) — the one place you most need it. This is a two-line fix.
  • Events carry no correlation identifier at all. Neither TransactionCreatedEvent nor BudgetOverspentEvent includes a request id or traceparent, so a notification can never be traced back to the transaction that caused it. Debugging "why did this user get this alert" requires timestamp archaeology across four services.
Why this ranks above most of the "Critical" items in sequencing

Every capacity number in this document is inferred from reading code. Some will be wrong. Without metrics you cannot rank fixes by measured impact, size an HPA (which needs a utilisation target derived from real load), set a meaningful AckWait or WriteTimeout (both of which must exceed a p99 you do not know), or tell whether a deploy improved anything. Instrument first, then fix in the order the data says. The one exception is F02 and F03 — those are unconditional defaults-are-wrong fixes that need no measurement to justify.

Remediation — days, and it pays for itself immediately
  • RED metrics per route via promhttp on a separate admin port (so /metrics is never publicly routable): request rate, error rate, and a duration histogram with buckets chosen around your SLO thresholds, not the library defaults.
  • Distributed tracing with otelgin and otelhttp. This is where a 32-span trace makes F01 visible in one screenshot — far more persuasive than any document, including this one.
  • Trace context across NATS. Inject traceparent into message headers and extract it in the consumer, so the async hop joins the same trace as the originating write.
  • The metrics that actually matter here: JetStream consumer lag per durable (the single best health signal for the write path); outbox depth and oldest-unpublished age; Mongo connection-pool saturation; per-backend HTTP client pool reuse ratio — which would have made F02 obvious from day one.
  • Exemplars linking histogram buckets to trace ids, so clicking a p99 spike in Grafana opens a real slow trace.

10. Frontend & edge delivery

F19 The frontend image cannot be promoted, and there is no edge Medium

frontend/Dockerfile, frontend/lib/api.ts, docker-compose.yml

  • Build-time API URL. NEXT_PUBLIC_API_BASE_URL is a build ARG inlined into the client bundle — correctly identified in the Dockerfile comment as a build-time concern. The infrastructure consequence is that you need a different image per environment, so you can never promote the exact bytes you tested in staging to production. That breaks the core promise of immutable artifacts.
  • No CDN and no cache strategy. Next.js static assets are content-hashed and immutable, which means they are ideal CDN candidates, and none of that is configured. Every asset request travels to the origin.
  • Single replica, no SSR caching, no revalidation strategy.
  • Tokens in localStorage, which the module honestly flags as a Phase 0 simplification with a plan to move to httpOnly cookies. Beyond the XSS exposure, it forces the cross-origin API design that makes CORS necessary at all.
Remediation

Serve the API same-origin. Route /api/* through the same ingress host as the frontend. This removes CORS entirely (deleting a whole class of bug, including the duplicate-header incident already documented in CLAUDE.md), enables httpOnly SameSite cookies, and lets a CDN sit in front of everything with per-path cache rules.

Make the API base runtime-configurable — a tiny /config.js served by the Node server and read at boot, or simply a relative /api path once same-origin. One image, promoted unchanged through every environment.

Put a CDN in front with immutable caching for hashed assets and short TTLs for HTML. This is the cheapest latency win available anywhere in the system and it scales to any RPM without touching your compute.

§Capacity model

Little's Law — L = λW, concurrency equals arrival rate times latency — is the tool for sizing this. A Go service handles tens of thousands of concurrent goroutines comfortably, so at a 20 ms mean latency a single gateway pod supports several thousand requests per second before goroutine concurrency is the binding constraint. Which means goroutines are never the ceiling here. The ceilings are elsewhere, and they are lower.

§Closing

The gap between this system and one that handles high volume is not a rewrite. The application architecture is sound and, crucially, the discipline that makes it sound — one place for every cross-cutting concern, documented trade-offs, enforced service boundaries — is exactly what makes the remediation tractable. Items 2, 3, 4, 5 and 11 in Phase A are collectively a few hours of work in shared/ and they move the system's failure mode from "falls over unpredictably" to "degrades measurably".

The two items that need real thought rather than configuration are F01, because it is a design decision and not a default, and F13, because without it you are optimising blind.
