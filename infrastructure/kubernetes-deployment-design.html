Purpose & how to use this document

This is the master design reference for putting all of Finora — five Go services, four MongoDBs, NATS, and the frontend — onto Kubernetes. It has two parts: get it working correctly on a local kind cluster on your MacBook first, then take the exact same application (repackaged for a different environment, not redesigned) onto a self-managed Kubernetes cluster you bootstrap yourself on EC2 instances, reachable at a real domain over HTTPS.

Read this like a design doc, not a copy-paste script. Each section states a decision, why it was made, and — where it matters — what was rejected and why. The actual manifests get built up incrementally, hands-on, service by service, in your own working sessions; this document is the map you're building toward, so you always know why the next step is the next step.

Scope decision

This document assumes: (1) storage for MongoDB is self-hosted inside the cluster in both environments — a StatefulSet + PersistentVolumeClaim per database, same "one Mongo per service" model you already have, just on real disks instead of Docker volumes; (2) deploys are driven directly by helm install / helm upgrade you run yourself — no GitOps/Argo CD yet, that's a deliberate later module once manual deploys are second nature; (3) the AWS phase is a self-managed cluster (kubeadm on plain EC2 instances) rather than EKS, so the control plane itself — etcd, the API server, the scheduler — is something you stand up and operate, not something AWS hands you.

Shared design principles

These apply in both environments. Everything below is in service of one of these.

  • One Helm chart, two values files. infrastructure/helm/finora/ is the single source of truth for what "Finora on Kubernetes" means. values-local.yaml and values-aws.yaml capture only what actually differs between environments (image registry, storage class, replica counts, ingress host, resource sizing) — not two parallel copies of the same manifests.
  • Config already thinks in these terms. Your services already read every setting from environment variables (shared/config, no hardcoded values) — that 12-factor discipline is exactly what makes a ConfigMap/Secret split a translation, not a redesign. .env.example is close to a literal index of what goes into each.
  • Service discovery doesn't change. Docker Compose gave you DNS-by-service-name (http://user-service:8081); Kubernetes Service objects give you the exact same thing inside a namespace. If you name every Service after its Compose service name, most of your existing env var values (USER_SERVICE_URL, NATS_URL, every *_MONGO_URI) don't need to change at all.
  • Secrets are never in a values file, committed or not. The Helm chart references an existing Secret object by name for anything sensitive (JWT_ACCESS_SECRET, JWT_REFRESH_SECRET); that Secret is created once, imperatively, outside of Helm's management, in every environment. Helm owns the shape of the deployment; it never owns the secret material.
  • Probes are not optional. Every Deployment/StatefulSet gets a liveness and readiness probe wired to the /live and /ready endpoints shared/health already gives you. A Pod with no readiness probe is "ready" the instant its process starts, whether or not it can actually reach Mongo — that's the exact gap /ready exists to close.
  • The same object model, different scale. Nothing about the Kubernetes objects changes between Mac and AWS. What changes is what's underneath them — a laptop's local-path-provisioner vs. real EBS volumes; kind's Docker-in-Docker networking vs. a real VPC. Learn the objects once on Mac; AWS is mostly learning what's underneath.

Part 1 — MacBook (kind)

Get the entire fleet running correctly and reachable at a fake local domain before AWS enters the picture at all.

1.1 Target end state

"Done" for Part 1 looks like: helm install finora infrastructure/helm/finora -f values-local.yaml brings up all 4 Mongos, NATS, all 5 Go services, and the frontend, every Pod passes its readiness probe, and you can open http://finora.local in a browser and use the app exactly the way you can today at http://localhost:3000 with docker compose up. This is functional parity with Compose, not a new feature.

1.2 Cluster topology

Single control-plane node is correct for this phase — kind's default. A multi-node kind config (one control-plane + two workers) is worth doing later purely to practice scheduling, node affinity, and pod topology spread — it's a good separate exercise, not a requirement for getting the app running.

Gotcha — recreate the cluster before Ingress

The finora kind cluster already created in an earlier session was created with kind create cluster --name finora and no extra config — it has no host port mapping, so an Ingress controller inside it is unreachable from your Mac's browser no matter what you install. Before doing Ingress work (§1.8), delete and recreate it with: 

kind delete cluster --name finora

cat <<'EOF' > kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
        protocol: TCP
      - containerPort: 443
        hostPort: 443
        protocol: TCP
EOF

kind create cluster --name finora --config kind-config.yaml

Everything already built (namespace, mongo-user Deployment/Service) is one kubectl apply -f infrastructure/kubernetes/ away from being back — nothing from those lessons is wasted, it folds directly into the Helm templates in §1.9.

1.3 Images

kind runs nodes as Docker containers with their own isolated image store — it does not see images sitting in your Mac's regular Docker Desktop image cache. Build, then explicitly load: 

# from the repo root, one per service — build context MUST be repo root
# (every Dockerfile also COPYs shared/)
docker build -f services/user-service/Dockerfile -t finora/user-service:local .
docker build -f services/expense-service/Dockerfile -t finora/expense-service:local .
docker build -f services/budget-service/Dockerfile -t finora/budget-service:local .
docker build -f services/notification-service/Dockerfile -t finora/notification-service:local .
docker build -f services/gateway/Dockerfile -t finora/gateway:local .
docker build -f frontend/Dockerfile -t finora/frontend:local \
  --build-arg NEXT_PUBLIC_API_BASE_URL=http://finora.local/api ./frontend

kind load docker-image finora/user-service:local finora/expense-service:local \
  finora/budget-service:local finora/notification-service:local \
  finora/gateway:local finora/frontend:local --name finora
Gotcha — the frontend image bakes in its API URL

NEXT_PUBLIC_API_BASE_URL is a Next.js build-time arg, not a runtime env var — it gets compiled into the static JS bundle. That means the frontend image is environment-specific: a finora/frontend:local image built for http://finora.local/api cannot be reused as-is against the AWS domain in Part 2. Rebuild (or better, build once per environment in CI later) with the right --build-arg for wherever it's actually going to run.

Every Deployment's imagePullPolicy should be IfNotPresent locally — with Never or the default (Always) you'll either force a registry pull that doesn't exist, or silently ignore a freshly rebuilt local image. This is exactly the kind of knob values-local.yaml exists for.

1.4 Configuration & secrets

Split .env.example into a ConfigMap for cross-cutting, non-sensitive values shared by every service, small per-service ConfigMaps for anything specific to one service (its own port, its own Mongo URI, any downstream service URL it calls directly), and one Secret for the two JWT signing keys. 

# finora-shared-config (ConfigMap) — applies to every Go service
LOG_LEVEL: info
SHUTDOWN_TIMEOUT: 10s
CORS_ALLOWED_ORIGINS: http://finora.local
RATE_LIMIT_REQUESTS_PER_SECOND: "10"
RATE_LIMIT_BURST: "20"
MAX_REQUEST_BODY_BYTES: "1048576"
OUTBOX_RELAY_INTERVAL: 2s
NATS_URL: nats://nats:4222

# user-service-config (ConfigMap) — this service only
USER_SERVICE_PORT: "8081"
USER_SERVICE_MONGO_URI: mongodb://mongo-user:27017/finora_users
JWT_ACCESS_TTL: 15m
JWT_REFRESH_TTL: 168h

Notice USER_SERVICE_MONGO_URI is unchanged from .env.example — it was already addressed by Compose service name, and a Kubernetes Service named mongo-user resolves exactly the same way. 

# created once, imperatively, per environment — never templated by Helm,
# never committed to git
kubectl create secret generic finora-secrets \
  --namespace finora \
  --from-literal=JWT_ACCESS_SECRET='<a-real-random-secret>' \
  --from-literal=JWT_REFRESH_SECRET='<a-different-real-random-secret>'
Why not put secrets in values.yaml at all, even gitignored?

Because the moment a secret lives in a values file, it's one careless git add -A or one copy-pasted Helm --values flag away from landing in a commit or a Slack message. Making the Secret an object Helm references rather than creates means there is no path by which the JWT keys ever pass through a YAML file on disk that Helm reads. This is also exactly the seam a future External Secrets Operator / Sealed Secrets upgrade would slot into without changing anything else about the chart.

1.5 Health probes

Every Go service already exposes /live, /ready, and /health via shared/health. The translation to Kubernetes is direct: 

livenessProbe:
  httpGet:
    path: /live
    port: 8081
  initialDelaySeconds: 5
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /ready
    port: 8081
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3
Why two separate probes instead of one

They answer different questions and a failure means a different action. Liveness failing means "this process is wedged, kill and restart the container" — reserve it for true deadlock/hang detection. Readiness failing means "this Pod is alive but shouldn't receive traffic right now" (e.g. Mongo connection dropped) — the Pod stays running and gets a chance to recover, it's just pulled out of the Service's routable endpoints in the meantime. Wiring both to the same endpoint means a transient dependency hiccup restarts your container instead of just quietly taking it out of rotation — a self-inflicted crash loop.

1.6 Workloads

WorkloadKindReplicas (local)Notes
mongo-user, mongo-expense, mongo-budget, mongo-notificationStatefulSet1 eachOne volumeClaimTemplates entry each — see §1.7
natsStatefulSet1JetStream needs a PVC too — its whole value proposition is durable delivery across restarts
user-service, expense-service, budget-service, notification-service, gatewayDeployment1 eachStateless — safe to scale up any time, no coordination needed
frontendDeployment1Stateless
Decision — StatefulSet, not Deployment, for Mongo and NATS

A StatefulSet gives each replica a stable, predictable name (mongo-user-0, not a random suffix) and its own PVC that follows that specific Pod identity across restarts — a Deployment's Pods are interchangeable by design, which is wrong for anything holding its own disk state. You're running one replica each today, so this matters less right now than it will the moment you consider a Mongo replica set — but the object choice should match what the workload is, not just what today's replica count happens to be.

1.7 Storage

kind ships a default StorageClass named standard, backed by local-path-provisioner — a PersistentVolumeClaim against it gets you a real, working volume with zero extra setup, living on the kind node's own container filesystem. 

volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 1Gi

1Gi per Mongo and NATS instance is plenty for local testing/dummy data. This is also the first knob that's genuinely different in Part 2 — AWS has no local-path-provisioner, so values-aws.yaml points storageClassName at a real EBS-backed class instead (§2.7). Nothing else about the StatefulSet changes.

1.8 Networking & Ingress

Install ingress-nginx's kind-specific manifest (it already targets nodes labeled ingress-ready=true, which the recreated cluster config in §1.2 sets): 

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
kubectl wait --namespace ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=90s

One Ingress object, one domain, path-based routing to the two things that actually receive external traffic:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: finora
  namespace: finora
spec:
  ingressClassName: nginx
  rules:
    - host: finora.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: gateway, port: { number: 8080 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: frontend, port: { number: 3000 } }

No path-rewrite annotation needed: the gateway's own routes already start with /api/v1/..., so the original request path can pass straight through unmodified. Add the fake local domain to your Mac's hosts file so the browser resolves it: 

echo "127.0.0.1 finora.local" | sudo tee -a /etc/hosts
Rejected — separate hostnames instead of one domain with path routing

Docker Compose exposes the frontend and gateway on two different ports of the same host; the Kubernetes-native equivalent of "two different ports" would be two different hostnames (app.finora.local / api.finora.local). Path-based routing under one host was chosen instead because it's what the real domain in Part 2 will actually do (nobody wants api.finora.com as a separate DNS record and cert to manage if a single Ingress with two path rules does the same job with one hostname, one cert, and simpler CORS — same-origin from the browser's perspective, since / and /api share a host). No TLS locally — cert-manager's Let's Encrypt integration (§2.8) requires a real, internet-reachable domain to complete an HTTP-01 challenge, so there's nothing to gain by fighting with self-signed certs on a laptop-only cluster.

1.9 Packaging as Helm

Recommended chart layout:

infrastructure/helm/finora/
├── Chart.yaml
├── values.yaml              # shared defaults across every environment
├── values-local.yaml        # kind overrides
├── values-aws.yaml          # kubeadm/EC2 overrides
└── templates/
    ├── _helpers.tpl          # common labels, name helpers
    ├── configmap-shared.yaml
    ├── ingress.yaml
    ├── mongo/
    │   └── statefulset.yaml  # ranges over values.mongo[] — one file, four instances
    ├── nats/
    │   ├── statefulset.yaml
    │   └── service.yaml
    └── services/
        ├── deployment.yaml   # ranges over values.services[] — one file, five services
        └── service.yaml
Decision — one templated file per resource type, not per service

The five Go services are structurally identical (one container, one port, the same probe shape, similar env layout) — that similarity is exactly what a Helm range over a list in values.yaml is for: 

# values.yaml (excerpt)
services:
  - name: user-service
    port: 8081
  - name: expense-service
    port: 8082
  - name: budget-service
    port: 8083
  - name: notification-service
    port: 8084
  - name: gateway
    port: 8080

# templates/services/deployment.yaml (excerpt)
{{- range .Values.services }}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .name }}
  namespace: {{ $.Release.Namespace }}
spec:
  replicas: {{ $.Values.replicaCount | default 1 }}
  selector:
    matchLabels: { app: {{ .name }} }
  template:
    metadata:
      labels: { app: {{ .name }} }
    spec:
      containers:
        - name: {{ .name }}
          image: "{{ $.Values.imageRegistry }}/{{ .name }}:{{ $.Values.imageTag }}"
          ports: [{ containerPort: {{ .port }} }]
          livenessProbe: { httpGet: { path: /live, port: {{ .port }} } }
          readinessProbe: { httpGet: { path: /ready, port: {{ .port }} } }
---
{{- end }}

Adding a sixth service later is a two-line addition to values.yaml, not a new template file. The trade-off, honestly: the actual rendered object for any one service only exists after helm template runs — slightly harder to eyeball than five separate files when something's wrong. helm template infrastructure/helm/finora -f values-local.yaml (no cluster contact, pure rendering) is the command that closes that gap when you need to see the real YAML.

1.10 Runbook

  1. Recreate the cluster with the Ingress-ready config (§1.2).
  2. kubectl apply -f infrastructure/kubernetes/namespace/
  3. Install ingress-nginx (§1.8) and wait for it to be ready.
  4. Build and kind load all six images (§1.3).
  5. kubectl create secret generic finora-secrets ... (§1.4) — once.
  6. Add finora.local to /etc/hosts.
  7. helm install finora infrastructure/helm/finora -f infrastructure/helm/finora/values-local.yaml
  8. kubectl get pods -w until every Pod is Running/Ready.
  9. Open http://finora.local.

1.11 Verification checklist

Verify, don't assume
  • kubectl get pods -A — everything Running, 0 unexpected restarts
  • kubectl get ingress -n finora — address populated, both paths present
  • Register a user, log in, create an account/transaction/budget through the actual browser UI
  • Deliberately delete a service Pod (kubectl delete pod <name>) mid-session — confirm the app recovers within a few seconds and the frontend doesn't need a hard refresh to keep working
  • Check an async event still completes end to end: create an over-budget transaction, confirm a notification eventually appears (same finora.transaction.created → ... → finora.budget.overspent chain as Compose, just running on different infrastructure underneath)

1.12 Teardown

kind delete cluster --name finora

Free, instant, and safe — nothing here costs money or touches anything outside your Mac.

Part 2 — AWS (self-managed Kubernetes on EC2)

Bootstrap a real cluster's control plane yourself with kubeadm, then run the same Helm chart against it.

2.1 Target end state

"Done" for Part 2: a kubeadm-bootstrapped cluster on your own EC2 instances, the same Helm chart deployed with values-aws.yaml, reachable at https://<YOUR_DOMAIN> with a valid Let's Encrypt certificate. This is explicitly a test cluster — single control-plane node, no HA, no autoscaling, no GitOps. The point is proving the deployment shape works on real cloud infrastructure you fully understand, not standing up something production-grade on the first attempt.

Why self-managed instead of EKS

EKS hands you a working control plane; the explicit goal here is understanding what's inside one. Everything in §2.3–§2.4 — kubeadm init, CNI installation, and every one of the add-ons EKS would otherwise have silently included — is exactly the part of Kubernetes internals that a managed offering exists specifically to hide from you. It's genuinely more work and more ways to get stuck, and it teaches things that don't come up day-to-day operating a managed cluster — that's the trade being made on purpose here, consistent with this project's stated goal of practicing the full platform-engineering skill set, not just the application layer.

2.2 Network & compute architecture

ComponentChoiceWhy
VPC10.0.0.0/16, one public subnet 10.0.0.0/24 in one AZSingle-subnet keeps this a one-NAT-Gateway-cheaper cluster; see cost callout below
Control plane1× t3.medium (2 vCPU / 4 GiB), 30GiB gp3 root volumeComfortable headroom for etcd + API server + scheduler + controller-manager at this scale
Workers2× t3.medium to start~13–14 small Pods total (4 Mongo + NATS + 5 Go services + frontend + ingress-nginx + cert-manager + metrics-server); resize to t3.large if kubectl top nodes shows sustained pressure
CNICalicoNetworkPolicy support (Flannel has none) — worth having even unused today, for a later hardening pass
Cost — the single-public-subnet trade-off

Putting workers in a private subnet (the "more correct" production pattern) requires a NAT Gateway for their outbound internet access (image pulls, package installs) — and a NAT Gateway bills ~$0.045/hr plus ~$0.045/GB processed, which quietly becomes the single largest line item on a small test cluster's bill. Everything in one public subnet with tight security groups (SSH and the API server open only to your own IP) is the pragmatic choice for a test cluster; graduate to private workers + NAT once this is a cluster you intend to leave running.

Gotcha — security groups need to allow Calico's overlay traffic

Calico's default networking mode encapsulates cross-node pod traffic in IP-in-IP (protocol number 4, not TCP or UDP). If your security group only opens TCP/UDP ports between nodes, pods on different EC2 instances will fail to reach each other with no obvious error at the Kubernetes layer — it looks like a DNS or service-mesh problem until you check the security group. Allow all traffic (or at minimum protocol 4) between the nodes' own security group and itself.

2.3 Bootstrapping with kubeadm

  1. Launch the EC2 instances, attach an IAM instance profile to every node (control plane and workers both need it — the cloud-controller-manager and EBS CSI driver run as Pods that could land on any node).
  2. On every node: install containerd, then kubeadm/kubelet/kubectl at the same <K8S_VERSION>.
  3. On the control-plane node: kubeadm init --pod-network-cidr=192.168.0.0/16 (Calico's expected default) — save the printed kubeadm join command, it contains the bootstrap token and CA hash workers need.
  4. Install Calico's manifest against the fresh control plane.
  5. On every worker node, run the saved kubeadm join command.
  6. kubectl get nodes from the control plane — all nodes Ready once Calico's Pods finish starting.

2.4 Cluster add-ons

This is the actual heart of "what EKS would have given you for free." A kubeadm cluster has no cloud provider integration at all out of the box — install these in order:

Add-onWhy it's needed
AWS cloud-controller-managerWithout it, a Service of type: LoadBalancer just sits in Pending forever — nothing in the cluster knows how to call the AWS API to provision an NLB. It's also what populates each Node object with its correct AWS instance type/AZ/region labels.
AWS EBS CSI driverSame gap for storage — without it there is no controller that can call CreateVolume/AttachVolume on AWS's behalf when a PVC is created.
metrics-serverPowers kubectl top nodes/pods, which is how you'll actually notice a worker needs resizing (§2.2) instead of finding out via an OOMKilled Pod.
ingress-nginxSame Ingress object and rules as Part 1 — install it with its Service as type: LoadBalancer this time, which the cloud-controller-manager turns into a real NLB.
cert-managerAutomates requesting and renewing the Let's Encrypt certificate — see §2.8.
Rejected (for now) — AWS Load Balancer Controller instead of ingress-nginx

The ALB-based controller is more "AWS-native" (a real Application Load Balancer with target groups instead of an NLB fronting the ingress-nginx Pods) and is the more common pairing with EKS specifically. It also needs more IAM permissions and its own webhook setup. ingress-nginx + NLB was chosen because it's the exact same Ingress object and controller as Part 1 — nothing about the actual routing rules needs to change moving from Mac to AWS, only what's provisioning the load balancer underneath. Worth revisiting once comfortable, not a wrong choice, just more surface area for a first cloud pass.

2.5 Registry & image pull auth

aws ecr create-repository --repository-name finora/user-service --region <AWS_REGION>
# ...one per service...

docker tag finora/user-service:local <ECR_REGISTRY>/finora/user-service:v1
docker push <ECR_REGISTRY>/finora/user-service:v1
Gotcha — ECR auth tokens expire every 12 hours

EKS-optimized AMIs ship with docker-credential-ecr-login pre-wired so kubelet image pulls always have a fresh token. Plain EC2 instances running your own kubeadm bootstrap do not have this by default — an imagePullSecret created once will silently start failing pulls (not existing running Pods — new ones, e.g. after a scale-up or node replacement) once that token expires. Fix it once, at node bootstrap time, by installing amazon-ecr-credential-helper and configuring containerd's registry config to use it — this gets a fresh token per-pull automatically, the same guarantee the EKS-optimized AMI gives you, without depending on an in-cluster CronJob to refresh a Secret.

2.6 Configuration & secrets

Identical mechanism to §1.4 — a shared ConfigMap, per-service ConfigMaps, one imperatively-created Secret. The only content change: CORS_ALLOWED_ORIGINS and the frontend's baked-in NEXT_PUBLIC_API_BASE_URL both become https://<YOUR_DOMAIN> instead of http://finora.local. Generate a genuinely different JWT_ACCESS_SECRET/JWT_REFRESH_SECRET for this environment — never reuse the local dev values here.

2.7 Storage (EBS)

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: gp3

values-aws.yaml sets storageClassName: ebs-sc instead of standard — the only change to every Mongo/NATS StatefulSet between environments.

Why WaitForFirstConsumer

The default immediate-binding mode can provision an EBS volume in an AZ that doesn't match where the Pod actually gets scheduled, leaving it permanently unschedulable. WaitForFirstConsumer delays volume creation until a Pod claiming it is actually scheduled, so the volume is always created in the right AZ. With a single-AZ subnet (§2.2) this specific failure mode can't happen yet — but it's the correct default the moment you add a second AZ, so there's no reason to set it any other way now.

2.8 DNS & TLS

  1. Once ingress-nginx's Service is up: kubectl get svc -n ingress-nginx ingress-nginx-controller — note the NLB's DNS name under EXTERNAL-IP.
  2. In Route53, create a hosted zone for <YOUR_DOMAIN> (if it isn't already), and an ALIAS record pointing <YOUR_DOMAIN> at that NLB DNS name.
  3. Install cert-manager, then a ClusterIssuer for Let's Encrypt using the HTTP-01 challenge type (DNS-01 needs Route53 API credentials wired into cert-manager — HTTP-01 needs nothing extra since the Ingress is already internet-reachable once step 2 propagates).
  4. Annotate the Ingress with cert-manager.io/cluster-issuer: letsencrypt-prod and add a tls: block naming a Secret for cert-manager to populate. It requests, stores, and auto-renews the certificate from there on — no manual renewal ever again.

2.9 Helm values overlay

# values-aws.yaml (excerpt)
imageRegistry: "<ECR_REGISTRY>/finora"
imageTag: v1
imagePullPolicy: Always
storageClassName: ebs-sc
ingress:
  host: "<YOUR_DOMAIN>"
  tls: true
resources:
  requests: { cpu: 100m, memory: 128Mi }

Same chart, same templates as Part 1 — this file is the entire diff. If a change to the app's behavior requires editing a template rather than a value here, that's a signal the chart drifted away from being environment-agnostic, worth stopping and fixing before it compounds.

2.10 Runbook

  1. Provision VPC, subnet, security groups, IAM instance profile, EC2 instances (§2.2).
  2. kubeadm init on control plane, install Calico, kubeadm join on workers (§2.3).
  3. Install cloud-controller-manager, EBS CSI driver, metrics-server, ingress-nginx, cert-manager (§2.4).
  4. Create ECR repositories, push all six images (§2.5).
  5. kubectl create secret generic finora-secrets ... with production values (§2.6).
  6. Apply the ebs-sc StorageClass (§2.7).
  7. helm install finora infrastructure/helm/finora -f infrastructure/helm/finora/values-aws.yaml
  8. Point DNS at the provisioned NLB, install the ClusterIssuer, confirm the certificate issues (§2.8).
  9. Open https://<YOUR_DOMAIN>.

2.11 Verification checklist

  • Same functional checklist as §1.11, against the real domain over HTTPS
  • kubectl get certificate -n finora — READY: True
  • kubectl top nodes — no node consistently pinned near its resource limits
  • Terminate a worker node deliberately (not the control plane) — confirm Pods reschedule onto the remaining worker within a couple of minutes
  • Confirm the ECR credential helper fix (§2.5) actually works: wait past the 12-hour token lifetime, then force a new Pod to schedule (e.g. kubectl rollout restart deployment/gateway) and confirm the image pull still succeeds

2.12 Cost & teardown

Every one of these bills continuously while it exists, whether or not you're using the app:

ResourceApproximate cost
3× t3.medium EC2 (control plane + 2 workers)~$0.0416/hr each ≈ $0.125/hr total
Network Load Balancer (from ingress-nginx)~$0.0225/hr + per-LCU usage
EBS volumes (root + Mongo/NATS PVCs)~$0.08/GB-month (gp3)
Route53 hosted zone$0.50/month flat + per-query

Teardown, in this order (order matters — deleting the LoadBalancer Service first lets the cloud-controller-manager actually deprovision the NLB instead of leaving it orphaned):

helm uninstall finora -n finora
kubectl delete -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/.../deploy.yaml   # frees the NLB
# then: terminate the 3 EC2 instances, delete their EBS volumes if not auto-deleted on termination,
# delete the Route53 records (and hosted zone, if you're done with it entirely)

2.13 Deliberately deferred

Named explicitly so nothing here reads as an oversight:

  • HA control plane — one etcd node is a single point of failure. Fine for a test cluster; not something to build a second module on top of until this one's fully understood.
  • GitOps (Argo CD) — deliberately deferred per CLAUDE.md's own roadmap; manual helm upgrade first.
  • Managed secrets (External Secrets Operator / AWS Secrets Manager) — the imperative kubectl create secret approach in §2.6 is the seam this slots into later, not a dead end.
  • Cluster autoscaler / node group scaling — fixed 2-worker count until there's a concrete reason to automate it.
  • NetworkPolicy enforcement — Calico supports it (§2.2), nothing enforces it yet.
  • Automated node patching / AMI rotation — nodes are hand-built for now.

Appendix: glossary

TermMeaning
PodSmallest deployable unit — one or more containers sharing a network namespace, scheduled together, no self-healing on its own.
DeploymentDeclares "N replicas of this Pod spec, always" for stateless workloads; owns a ReplicaSet that does the actual reconciling.
StatefulSetLike a Deployment, but each replica gets a stable name and its own persistent volume tied to that specific replica identity.
ServiceStable DNS name + virtual IP load-balancing across Pods matched by label selector.
IngressHTTP(S) routing rules (host/path → Service) fronted by an Ingress controller (here, ingress-nginx).
ConfigMap / SecretExternalized configuration injected as env vars or files; Secret is base64-encoded at rest, not encrypted by default — treat it as "not-plaintext," not "safe."
PersistentVolumeClaim (PVC)A request for storage, satisfied by a StorageClass's provisioner (local-path-provisioner locally, the EBS CSI driver on AWS).
kubeadmThe tool that bootstraps a Kubernetes control plane (and joins workers to it) on plain machines — what kind and most managed-cluster CLIs use internally.
Cloud controller managerThe component that lets in-cluster objects (Service type=LoadBalancer, Node metadata) trigger real cloud-provider API calls — absent by default on any self-bootstrapped cluster.
CSI driverContainer Storage Interface — the plugin that lets Kubernetes provision/attach real cloud disks for PVCs.
